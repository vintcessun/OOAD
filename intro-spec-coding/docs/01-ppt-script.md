## 第 1 页 · 封面

**标题**：从 Prompt 到 Executable Spec：Spec Coding 范式调研与工具链实测

**画面**：标题；副标题「Claude Code / Codex / OpenCode / Cursor / OpenSpec · 3 档规格 · 81 个实验 run」；小组名。

**讲稿**：
各位好，今天我们组分享的主题是 Spec Coding，也就是「先定规格，再写代码」。

市面上谈 AI 编程工具，常见的做法是横评：哪个工具更聪明，哪个分数更高。我们这次换了一个问题：同一个开发任务，规格写得清不清楚，对 AI 写出来的代码影响有多大？工具和工作流又各自贡献了多少？

为了回答这个问题，我们没有只做文献调研，而是搭了一个小型 benchmark，真实跑了81次实验。

## 第 2 页 · 今天回答三个问题

**画面**：三行大字。

- RQ1 规格写得越细，AI 一次做对的概率是否越高？
- RQ2 同一个模型，换不同的 Coding Agent，差别有多大？
- RQ3 在 Agent 之外再加一层 Spec 工作流（OpenSpec），还有没有额外收益？

**讲稿**：
整场分享围绕这三个问题展开。

第一个问题关于规格本身，第二个关于工具，第三个关于流程。之所以把工具和流程拆开，是因为它们根本不在一个层次。这一点后面会专门讲。

先剧透一下结论的形状：三个因素里，规格的影响最大，工具的影响最小，流程的作用和大家想的不太一样。

---

## 第 3 页 · 一句话需求里藏着多少分歧

**画面**：左边一句需求「用户可以给订单使用优惠券，支持固定金额和百分比折扣」；右边五个问号：

- 百分比算出小数怎么取整？
- 折扣比订单金额还大怎么办？
- 到期那一秒算不算过期？
- 一单能不能叠两张券？
- 券不存在时返回 400 还是 404？

**讲稿**：
看左边这句需求，大家都觉得自己听懂了。可是一写代码，右边这五个问题都必须做出决定，而需求里一个答案都没有。

这五个问题，每个都有不止一种「合理」的写法。人类程序员遇到时会去问产品经理；AI 遇到时，绝大多数情况下会自己选一个，然后继续往下写。

---

## 第 4 页 · AI 缺的不是编码能力，是决策边界

**画面**：一句大字：「AI lacks decision boundaries, not coding ability.」下面一行小字：Prompt Coding 里的决策是隐式猜出来的；Spec Coding 里的决策是显式写下来的。

**讲稿**：
所以我们的第一个判断是：今天的模型写一个优惠券接口完全没问题，它缺的是「哪种写法才算对」的边界。

在 Prompt Coding 里，这些边界由模型隐式地猜，人只能事后读代码、跑测试，才知道它猜了什么。Spec Coding 要做的，就是把这些决策提前写下来，让它们可以被审查，也可以被验证。

---

## 第 5 页 · 什么是 Spec Coding

**画面**：流程图 `Idea → Spec → Plan → Code → Verify`，Spec 和 Verify 之间画一条回指的箭头，标注「验收依据」。

**讲稿**：
Spec Coding 的流程是：先有想法，再写规格，然后让 Agent 出计划、写代码，最后对照规格验收。

关键在这条回指的箭头：规格不只是给 AI 的输入，也是验收的依据。先解决 What，再解决 How。规格写完那一刻，什么叫「做对了」就已经确定了，而不是等代码写完再争论。

---

## 第 6 页 · 先定规格不是新想法

**画面**：时间轴：形式化方法（Z、VDM）→ 契约式设计（Eiffel）→ TDD / BDD（Given/When/Then）→ OpenAPI → Copilot 补全 → Agentic Coding（Claude Code、Codex、OpenCode、Cursor Agent）→ Spec-Driven Workflow（OpenSpec、Spec Kit、Kiro）。

**讲稿**：
先定规格再写代码并不是 AI 时代的新发明。形式化方法、契约式设计、BDD 的 Given/When/Then、OpenAPI 都是这个思路。

这条时间轴上有两个趋势：规格越来越可执行，从散文变成测试、变成接口描述；规格也越来越贴近代码库，从需求文档变成仓库里的 Markdown。

AI 带来的变化是规格的读者多了一个 Agent。规格因此必须让机器读得懂、判得了对错。

---

## 第 7 页 · 工具版图：两个层次

**画面**：上下两层。

- 上层「Spec 工作流」：OpenSpec（proposal → specs → design → tasks → apply → archive）
- 下层「Coding Agent」：Cursor、Claude Code、Codex、OpenCode

中间一句：**Agent 解决「AI 怎么写代码」，OpenSpec 解决「AI 写代码之前，怎么确定该写什么」。**

**讲稿**：
这页是整场分享的主线。

Cursor、Claude Code、Codex、OpenCode 都是 Coding Agent，负责读代码、改代码、跑命令。OpenSpec 不一样，它自己不写一行代码，而是一套工作流：先写提案、写增量规格、写设计、拆任务，最后才让 Agent 动手。

所以拿 OpenSpec 和 Claude Code 比谁好，是在比两个不同层次的东西。正确的问法是：同一个 Agent，加不加 OpenSpec，差多少？

---

## 第 8 页 · 各家 Agent 的「规格入口」

**画面**：表格。

| 工具 | 计划 | 持久化规则 | 自动化 |
|---|---|---|---|
| Cursor | Plan Mode | `.cursor/rules`、`AGENTS.md` | Cursor CLI |
| Claude Code | Plan 权限模式 | `CLAUDE.md`、Skills | `claude -p` |
| Codex | — | `AGENTS.md`、Skills | `codex exec` |
| OpenCode | Plan Agent | `AGENTS.md`、Skills | `opencode run` |

**讲稿**：
几家 Agent 的「规格入口」其实很像：都有先出计划再动手的模式，都支持把项目约定写进仓库里的规则文件，都有非交互的自动化模式。

这也意味着单论「支持 Spec」，几家没有本质区别。区别在体验和生态：Cursor 在 IDE 里，另外三个在终端；OpenCode 是开源的，可以接任意模型。

## 第 9 页 · OpenSpec 怎么接到 Agent 上

**画面**：`openspec init --tools claude|codex|opencode|cursor` → 在仓库里写入 6 个 Skill（以及命令）→ Agent 按 Skill 调用 `openspec new change` / `instructions` / `validate`。右侧放一张实验中真实生成的目录树：`proposal.md`、`specs/…/spec.md`、`design.md`、`tasks.md`。

**讲稿**：
OpenSpec 接入 Agent 的方式很朴素：初始化时，往仓库里写几份 Skill 说明，教 Agent 按什么顺序做事、调用哪些命令。

右边是我们实验里 Agent 真实生成的产物：一个提案、一份按场景写的增量规格、一份设计文档、一张任务清单。任务清单里每一项完成后都会被勾掉。

这些文档是 OpenSpec 的核心价值所在，后面的实验会说明为什么。

---

## 第 10 页 · 实验设计：3 × 2 因子 + 基线

**画面**：矩阵图。行是 Claude Code / Codex / OpenCode，列是「原生」和「+OpenSpec」，旁边单列「Prompt-only（单次调用，无工具）」。外层乘以 L1 / L2 / L3，再乘以 3 次重复。下方：`7 × 3 × 3 = 63 个 run`，另有坏规格 18 个 run。

**讲稿**：
实验设计上，我们没有做「工具三选一」的横评，而是做了一个因子实验。三个 Agent 各跑原生和加 OpenSpec 两组：同一行内对比，得到 OpenSpec 的效果；同一列内对比，得到 Agent 的差异。

另外加了一个最朴素的基线：不给任何工具，把整个仓库和需求一次性发给模型，让它直接吐出代码。这代表最原始的 Prompt Coding。

每个组合在三档规格下各跑三次，共 63 次；另有 18 次坏规格实验。

---

## 第 11 页 · 怎么保证公平

**画面**：五个图标。

- **同一模型**：全部用 DeepSeek `deepseek-flash`
- **同一提示词**：原生组一字不差；OpenSpec 组只换第一句
- **干净环境**：每个 run 一个新容器，从同一个提交开始，没有任何隐形规则文件
- **隐藏测试**：Agent 看不到；它退出后，工作区冻结，再放进测试
- **不干预**：不说「继续」，不反馈测试结果

**讲稿**：
公平性是这个实验最花功夫的地方。

最重要的一点是同一模型。如果 Claude Code 用 Claude、Codex 用 GPT，测出来的是模型差异，不是工具差异。所以三个 Agent 都按 DeepSeek 官方接入文档，接到同一个 deepseek-flash 上。

Cursor 只能用它托管的模型，没法接这个端点，所以没进受控对比。我们留了手工补测的脚本，组员在 Cursor 里跑完可以用同一套测试打分，结果单独列出。

另外，每个 run 都在新容器里，看不到我们电脑上的任何配置，也看不到答案；Agent 自己说做完了，就立刻冻结评分。

## 第 12 页 · 被测任务与三档规格

**画面**：任务「`POST /orders/:id/apply-coupon`」。三列卡片：

- **L1**（5 行，质量分 5）：路径 + 一句话
- **L2**（25 行，质量分 19）：5 条规则 + 3 条验收
- **L3**（88 行，质量分 100）：14 条编号需求 + 错误码表 + 10 条 Given/When/Then

**讲稿**：
被测任务是给订单使用优惠券。它不大，但规则密集：九类业务规则、一堆边界条件、十种错误码，还要保证三张表的事务一致性。

三档规格分别是：一句话；照搬思路文档的结构化示例，有五条规则、三条验收；以及完整、可判定的规格，也只有 88 行。

右上角的质量分，是我们写的一个规格检查器打的分。它看规格有没有编号需求、验收标准、边界、错误码这些部件，碰到「适当」「合理」这类词就扣分。

## 第 13 页 · 评分：不只看「能不能跑」

**画面**：三层金字塔。

- Outcome（做对了吗）：一次通过率、正确性
- Alignment（按规格做的吗）：需求覆盖、错误码符合度、范围控制
- Economics（做对花了多少）：时间、token、花费

下面一行：41 个隐藏测试 × 严重度加权；总分 = 0.35C + 0.20A + 0.15R + 0.10Q + 0.10E + 0.10S。

**讲稿**：
传统的 AI 编程评测只问代码能不能跑，Spec Coding 还要问两件事：是不是按规格做的，做对花了多少成本。

我们准备了 41 个 Agent 看不到的验收测试，按严重度加权。

有一个细节：「一次通过」只看行为对不对，错误码是否和规格完全一致单独计分。原因是，一个返回 500 的拒绝，和一个返回规定错误码的拒绝，功能上都算「拒绝了」，但只有后者符合规格。我们想把这两种情况分开看。

## 第 14 页 · 结果 1：规格越细，越能做对

**画面**：柱状图，横轴 L1 / L2 / L3，纵轴「隐藏测试加权通过率」，每档 7 根柱子（7 种执行方式），并标出一次通过率。（表 1、表 4c）

图上标注三组数字：

- L1：7 种执行方式的隐藏测试通过率在 82.7%–83.7%，一次通过 0/21；
- L2：69.3%–79.3%（单次调用基线 47.3%），一次通过 0/21；
- L3：全部 100%，一次通过 21/21。

**讲稿**：
先看第一个问题的答案。

拿到完整规格 L3 时，7 种执行方式、21 次运行全部一次通过，41 个隐藏测试一个不漏。最朴素的「单次调用、不给任何工具」也是 3 次全对。

拿到一句话或中粒度规格时，21 加 21 次运行，一次通过的是 0。

所以在这个任务上，规格写到可判定以后，用哪个工具已经不影响对错了；规格写不清楚，换哪个工具都救不回来。

不过大家注意中间那一档：L2 比 L1 还低。这是我们最意外的结果，下一页专门讲。

---

## 第 15 页 · 反直觉：只写一半的规格，比不写更糟

**画面**：L1 与 L2 并排，标出 L2 通过率低于 L1；下面放一段真实 diff 对比：

- L1 的 Agent 自己加上了 `if (order.status !== "PENDING")` 和「订单已用过券」的检查；
- L2 的 Agent 没有这两条。

（表 4c、调研报告 §5.3）

**讲稿**：
L2 是我们原样照搬思路文档里的中粒度示例：一个接口、五条规则、三条验收。按常识，它应该比一句话好。可实际上，7 种执行方式在 L2 下都比 L1 差，差距从 4 到 36 个百分点。

我们把失败的测试逐个拆开。差距主要来自几条 L2 没写的规则：一张订单不能用两张券，已取消、已支付的订单不能用券。L2 下 18 次 Agent 运行里，「一单一券」失败 17 次；同样没写这条规则的 L1，失败 0 次。

为什么一句话反而更好？我们的解释是：拿到一句话，Agent 会去通读代码库。表结构里有用量字段、有用券记录表，已有代码里有订单状态检查，它就顺着这些把规则补上了。拿到一份看起来很完整的清单，它就把清单当成了全部需求。

我们把这个现象叫作「清单锚定」。这是一个有证据的假设，还谈不上结论：我们只有一个代码库，而且这个代码库很「会说话」。

## 第 16 页 · 规格改变的是「错在哪」

**画面**：两个饼图：L1 的失败原因、L2 的失败原因；L3 标注「无失败」或剩余的少量失败。（表 4）

**讲稿**：
再看错在哪里。

L1 的失败里，三分之二是错误码名字不一致，三成左右是边界问题，比如到期那一秒算不算过期。真正漏掉需求、或者做错需求的，是 0。也就是说，L1 下的 Agent 功能都做对了，只是在约定上和规格作者想的不一样。

L2 多出了两类错误：漏需求占 18%，错误假设占 12%。这两类正好对应上一页的清单锚定。

到 L3，失败为零。

思路文档里预言过：提高规格粒度，主要是减少错误假设，而不是让代码更漂亮。我们的数据支持这一点。只不过在这个代码库上，错误假设主要出现在半规格里。

## 第 17 页 · 结果 2：同一模型下，Agent 之间差距很小

**画面**：同一规格下三个 Agent 的六维雷达图，三条线几乎重叠；旁边一行字：「换 Agent 带来的差距 ≪ 换规格带来的差距」。（表 2）

**讲稿**：
第二个问题，换 Agent 差多少。

答案是：在同一个模型下，差得很少。

- L1 下，三个 Agent 的通过率极差只有 1 个百分点；
- L2 下最大 5.6 个百分点；
- L3 下都是 100%。

对比一下，从 L1 换到 L3，带来的是 17 个百分点。

三者的差别主要在成本和工作方式。Codex 调用工具最少，单次花费和 OpenCode 并列最低；Claude Code 单次花费最高，但也不过一毛多钱。三者都遵守了分层架构，没有乱改无关文件。

所以我们的建议是：不要用「哪个 Agent 分数最高」来选型。差距很小，而且会随着版本更新变化。

---

## 第 18 页 · 结果 3：OpenSpec 的账怎么算

**画面**：左边「原生 → +OpenSpec」的通过率变化（三个 Agent × 三档）；右边耗时和花费的倍数。（表 4b、表 3）

**讲稿**：
第三个问题，OpenSpec 值不值。

先说正确率：没有稳定提高。

- L1 和 L3 下几乎没有变化；
- L2 下三个 Agent 的变化分别是加 10 个点、减 5 个点、加 2 个点，方向都不一致。每格只有 3 次，我们不能据此说它有效。

再说代价，这个很稳定：花费是原来的 1.4 到 2.6 倍，时间是 1.6 到 3.4 倍。实验里所有超过 15 分钟的运行，全部是 OpenSpec 组。

还有一个容易误读的地方：L3 下 OpenSpec 组总分 93，原生组 98。这 5 分全部扣在效率上，正确性和规格符合度都是满分。

那它到底值在哪里？看下一页。

---

## 第 19 页 · OpenSpec 真正的价值：错误在写代码之前就能被看见

**画面**：截取实验中一份真实的 `design.md`：

> **Non-Goals:** Enforcing `usage_limit` or preventing a coupon from being applied more than once. TASK.md does not list these rules.

旁边标注：这两条正是隐藏测试里失败的需求。

**讲稿**：
这一页是我们觉得整场最有价值的发现。

这是一个 L2 规格加 OpenSpec 的 run 生成的设计文档。在「不做什么」一节里，Agent 白纸黑字写着：不处理用量上限，也不阻止一张券被重复使用，因为 TASK.md 没有列出这些规则。

这两条正是后来隐藏测试里失败的需求。也就是说，OpenSpec 没有让 Agent 自动做对，但它让 Agent 的误解在写代码之前，就以人能读懂的方式摆在了桌面上。一个审查者花两分钟看完这份设计，就能把需求补上。

没有这一步，同样的缺口只能等测试失败，甚至等到上线以后才被发现。

## 第 20 页 · 成本—正确率

**画面**：散点图，横轴「每个 run 的花费（元）」或耗时，纵轴「隐藏测试通过率」；点按执行方式着色，左上角标「理想区」。（表 3）

**讲稿**：
把成本和正确率放在一张图上看。

横轴是单次运行的模型费用，按高峰价统一折算；纵轴是通过率。

- 原生 Agent 一次一毛到一毛七；
- 加了 OpenSpec 是两毛到三毛三；
- 单次调用基线一毛到一毛四，并不比原生 Agent 便宜多少，因为它输出的 token 里大部分是模型的思考过程。

纵轴上，三条水平带分得很清楚：L3 在最上面，L1 在中间，L2 在下面。也就是说，决定点落在哪一层的是规格，横向位置才是工具和流程决定的。

对中小团队来说，模型费用几乎可以忽略。我们整个实验 81 次运行，一共花了十几块钱。真正贵的是人：写一份 L3 规格的时间，以及认真审 OpenSpec 产物的时间。选型时应该比较这部分成本。

## 第 21 页 · 坏规格：谁能发现规格本身的问题

**画面**：三类坏规格（歧义、缺失、冲突），每类一句例子；表格列出 6 种执行方式是否指出了缺陷。（表 5）

**讲稿**：
最后一组实验：故意给 Agent 有问题的规格，看谁能发现。

我们从 L3 改出三份坏规格：

- 一份写得含糊，比如「大额订单给予适当上限」；
- 一份漏了一条规则：折扣比订单金额大时怎么办；
- 一份前后矛盾：规则说最多优惠 100 元，验收示例却要求优惠 200 元。

结果分三类：

- 矛盾最容易发现。6 次运行全部指出了两处冲突，并说明了自己选哪一边。
- 含糊和缺失大多被悄悄处理掉了。「折扣大于金额」这一条，6 次运行全部按字面实现，只有 2 次提了一句。
- OpenSpec 组和原生组发现问题的次数差不多，10 比 9。区别在于：原生 Agent 的说明写在聊天里，会话一关就没了；OpenSpec 组把冲突和取舍写进了设计文档，留在仓库里。

我们还发现了一个反例：有一次 OpenSpec 运行在设计文档里写「规格已经明确规定了取整方式」，可规格其实没规定。流程不能保证 Agent 真的想清楚了，它只是让 Agent 的想法可以被检查。

## 第 22 页 · 这个实验不能说明什么

**画面**：五条局限。

- 只有一个任务、一个代码库，代码库本身很「会说话」
- 只有一个模型（deepseek-flash）；换更强或更弱的模型，结论的幅度可能不同
- 每格 3 次，适合看方向，不适合做显著性检验
- Cursor 没进受控对比
- 中途 API 变慢，超时上限从 15 分钟调到 25 分钟，超时的 run 已按新规则重跑

**讲稿**：
最后要诚实地说清楚，这个实验不能说明什么。

我们只有一个任务、一个模型，每个组合跑三次，适合看方向和量级，不能当成严格的统计结论。被测代码库结构清晰，表结构里已经藏着大部分业务概念，这对 L1 很友好；换一个更乱的老代码库，L1 的表现很可能更差。

另外，实验中途 DeepSeek 的输出速度掉到原来的三分之一左右。几个 OpenSpec 的 run 撞上了 15 分钟的上限，我们把上限调到 25 分钟，并把超时的 run 按新规则重跑。原始的超时记录也保留在仓库里。

## 第 23 页 · 选型：先看规格，再看工具

**画面**：二维框架，横轴任务复杂度，纵轴协作与追溯要求，四个象限：

- ① 简单、单人：Agent 直接做 + 项目规则文件
- ② 复杂、单人：可判定规格（L3 模板）+ Agent 计划模式
- ③ 简单、多人：轻量规格进 PR + 审计划
- ④ 复杂、多人：OpenSpec + Agent + 测试/CI，人审 proposal 和 design

**讲稿**：
基于实验，我们给中小团队的选型建议不是一个排行榜，而是这个二维框架。

横轴是任务有多复杂，纵轴是需要多少协作和追溯。

- 简单的单人任务，任何 Agent 加一份项目规则文件就够了。
- 复杂但单人负责的任务，最划算的投入是把规格写到可判定。
- 多人协作、需求经常变的模块，才值得上 OpenSpec。而且一定要有人审它产出的提案和设计，否则只是多花了时间。

工具本身：

- 在 IDE 里工作选 Cursor；
- 要自动化、接 CI，选 Claude Code 或 Codex；
- 想自由换模型、控制成本，选 OpenCode。

在我们的实验里，它们用同一个模型时差距很小。

## 第 24 页 · 结论

**画面**：两行大字。

> **Prompt Coding**：Tell AI what you want.
> **Spec Coding**：Define what "correct" means before AI writes code.

下方小字：规格要可判定、可验证、无歧义；目标是最低限度的充分规格（Minimum Sufficient Spec），而不是最长的规格。

**讲稿**：
最后用两句话收尾。

Prompt Coding 是告诉 AI 你想要什么；Spec Coding 是在 AI 写代码之前，先定义清楚什么叫「对」。

我们的实验给这句话补了三个注脚：

1. 规格写到可判定，换哪个工具都能做对；
2. 只写一半的规格最危险，它会把 Agent 的注意力锁在清单上；
3. OpenSpec 这样的工作流不会替你想清楚需求，但它能把没想清楚的地方，在写代码之前暴露出来。

所以 Spec Coding 的目标不是把规格写得越长越好，而是找到刚好够用、又能被验证的那一份规格。谢谢大家。
