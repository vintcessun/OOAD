# 中小团队 Spec Coding 工具选型指南

**2026 年 10 月 9 日** · 依据：本组调研（调研报告第 2–3 节）+ 对照实验（`bench/results/summary.md`）

> 适用对象：3–15 人的开发团队，已经或准备在日常开发中使用 AI Coding Agent，想知道该不该上「规格驱动」、上到什么程度、选什么工具。
>
> 这份指南不给出工具排行榜。实验里同一模型下几个 Agent 的差距，远小于规格写得好不好带来的差距。**先决定规格怎么写，再选工具。**

---

## 1. 三条先于选型的原则

### 原则 1：规格质量比工具选择更重要

实验中，同一个需求换成完整、可判定的规格（L3）后，所有执行方式都能稳定做对。差别甚至包括「没有工具、只调用一次模型」的方式。反过来，规格不完整时，换哪个 Agent 都救不回来（调研报告 §5.1；汇总表 1、表 4c）。

所以团队引入 Spec Coding 的第一步不是买工具，而是**约定规格的最低标准**（第 3 节的模板）。

### 原则 2：只写一半的规格可能比不写更危险

实验里有一个反直觉的结果：只列了 5 条规则的中粒度规格（L2），通过率低于一句话需求（L1）。原因是：

- 拿到一句话需求时，Agent 会去读代码库，从表结构、已有错误码、已有状态机里推断隐含规则；
- 拿到一份「看起来很完整」的规则清单时，Agent 倾向于只实现清单上的内容。

例如，L2 下多个 run 都没有检查「订单必须是 PENDING」和「一单只能用一张券」。这两条规则 L2 没写，L1 也没写，但 L1 下的 Agent 自己补上了（调研报告 §5.2）。

所以，**规格要么写到可判定，要么明确写出「未列出的规则按现有代码约定处理」**。不要交出一份「看起来完整、实际有缺口」的清单。

### 原则 3：Spec 工作流的价值在「可审查」，不在「自动做对」

OpenSpec 不会自己补出规格里缺的需求。但它会在写代码之前，把 Agent 对需求的理解写成 proposal、spec、design、tasks 四份文档。

实验里，有一个 L2 run 的 `design.md` 明确写着：

> Non-Goals: Enforcing `usage_limit` or preventing a coupon from being applied more than once. TASK.md does not list these rules.

人只要花两分钟审一下这份设计，就能在写代码之前发现缺了两条需求。没有这一步，同样的缺口只能等测试失败、甚至上线之后才发现。

代价是时间和 token：同一规格下，OpenSpec 组的花费约为原生 Agent 的 1.4–2.6 倍，耗时约为 1.6–3.4 倍。而且它没有稳定提高正确率（调研报告 §5.5；汇总表 3、表 4b）。

## 2. 二维选型框架

两个维度：

- **任务复杂度**：要做的需求有多少条业务规则、边界条件、跨表状态变化。
- **协作与稳定性**：需求是否会被多人反复讨论和修改，是否需要事后追溯「这条需求落在哪段代码」。

```
            协作 / 追溯要求
               高 │  ③ 轻量 Spec + Agent Plan      │  ④ OpenSpec + Agent + 测试/CI
                  │   （规格模板 + PR 审查）        │   （proposal 审查 → apply → archive）
                  │                                 │
               低 │  ① Agent 直接做                  │  ② 可判定规格 + Agent Plan 模式
                  │   （一句话 + 项目规则文件）      │   （规格模板写到 L3）
                  └─────────────────────────────────┴──────────────────────────────────→
                              低                         任务复杂度                   高
```

| 象限 | 典型场景 | 推荐做法 | 不推荐 |
|---|---|---|---|
| ① 低复杂度、低协作 | 改文案、加字段、单人小功能 | 任意 Agent 直接做；在项目规则文件里写清分层、错误码、时间注入等约定（`CLAUDE.md` / `AGENTS.md` / `.cursor/rules`） | 为小改动写完整 proposal |
| ② 高复杂度、低协作 | 单人负责的业务规则密集功能（计费、优惠、权限） | 按第 3 节模板写到 L3（编号需求 + 错误码表 + Given/When/Then），再让 Agent 先出计划后实现 | 只给规则清单的「半规格」 |
| ③ 低复杂度、高协作 | 多人维护的 CRUD、接口改动 | 轻量规格模板放进 PR 描述；Agent Plan 模式先出计划，PR 里审计划 | 强制全员走完整 Spec 流程 |
| ④ 高复杂度、高协作 | 需求反复变化、需要追溯和审计的模块 | OpenSpec + 任意 Agent：人审 proposal/design，Agent apply，测试和 CI 验收；变更完成后 `archive` 沉淀为长期 spec | 跳过人审，把 OpenSpec 当成「自动做对」的按钮 |

## 3. 最低可用规格模板（L3 的精简版）

实验里，L3 规格让所有执行方式稳定通过，而它只有 88 行。中小团队可以从下面这份模板开始，每个需求控制在一屏到两屏：

```markdown
# 任务：<一句话>

## API 契约
<方法 路径>，请求体示例，成功响应与哪个已有接口同形

## 业务规则（编号，每条可判定）
- REQ-01 <条件>，否则 <错误码>
- REQ-02 <公式，写清取整方式和上下限>
- REQ-03 <边界：用 <= / < 写清等号归属；时间从哪里取>
- ...

## 错误码（按检查顺序）
| 顺序 | 条件 | HTTP | code |

## 验收（Given / When / Then，覆盖每条边界）
- AC-01 Given … When … Then …

## 约束
分层、不改表结构、不加依赖、必须补测试；未列出的规则按现有代码约定处理
```

写规格时自查四个问题：

1. 每条规则能不能写成一个测试？
2. 每个边界的等号归属写了吗？
3. 每种失败返回什么，写了吗？
4. 有没有「适当」「合理」「大额」这类无法判定的词？（`bench/runner/spec-lint.mjs` 会把它们标出来）

## 4. 工具怎么选

前提：本组实验让 Claude Code、Codex、OpenCode 用同一个模型（DeepSeek `deepseek-flash`）对比。在这个前提下，三者在规格完整时都能做对，差别主要在成本、速度和工作方式（调研报告 §5.4；汇总表 2、表 3）。Cursor 因为只能使用它托管的模型，没有进入受控对比（调研报告 §3.3）。下表的建议综合了实验数据和工具机制。

| 你的团队 | 首选 | 理由 |
|---|---|---|
| 主要在 IDE 里写代码，想要最低上手成本 | **Cursor**（Agent + Plan Mode + Rules） | 在 IDE 内完成计划和审查；Rules 可版本化放进仓库。需要接受它的订阅和托管模型 |
| 习惯终端、要接 CI 或脚本自动化 | **Claude Code** 或 **Codex** | 都有非交互模式（`claude -p`、`codex exec`），都能输出结构化日志，本实验的自动化 runner 就靠这一点。按团队已有账号和模型二选一 |
| 预算敏感、想自由切换国产或开源模型 | **OpenCode** | 开源，按提供方接入任意模型；本实验中它与另外两个 Agent 用同一模型时表现接近 |
| 需求多人反复讨论、需要追溯 | **OpenSpec + 上面任意一个** | OpenSpec 支持 Claude Code、Codex、OpenCode、Cursor 等多种 Agent（`openspec init --tools …`），换 Agent 不用换流程 |
| 刚开始尝试 | **任意 Agent + 第 3 节模板** | 先把规格写到可判定，再考虑要不要全面流程化 |

**不建议的做法**：

- 用「哪个工具分数最高」做决定。同模型下差距很小，而且会随模型更新变化。
- 规格没写清就上 OpenSpec。工作流会把模糊的需求原样写进 proposal，只是多花了时间。
- 让 Agent 自己判断「需求做完了没有」。验收标准和测试应该在 Agent 开工前由人写好（实验里的隐藏测试就是这个角色）。

## 5. 落地路线（4 周）

| 周 | 做什么 | 产出 |
|---|---|---|
| 1 | 选一个 Agent，在仓库里写项目规则文件（分层、错误码格式、时间注入、测试命令） | `CLAUDE.md` / `AGENTS.md` |
| 2 | 采用第 3 节规格模板，下一个中等复杂度需求按模板写，人工写 3–5 条验收测试 | 第一份 L3 规格 + 验收测试 |
| 3 | 在 PR 模板里加「规格链接 + Agent 计划」两栏，评审时先审规格和计划，再审代码 | PR 模板 |
| 4 | 选一个多人协作的模块试用 OpenSpec：人审 proposal 和 design，Agent apply，完成后 archive | `openspec/` 目录、复盘：多花的时间换来了什么 |

每个阶段都记录两个数：**一次通过率**（第一次提交时验收测试是否全部通过），以及**返工时间**。第 4 周结束时，用这两个数决定 OpenSpec 要不要推广，而不是凭感觉。

## 6. 成本参考

实验用的是 DeepSeek `deepseek-flash`。一个约 300 行改动的功能：

- 原生 Agent 一次花费约 ¥0.10–0.17（按高峰价折算），耗时约 4–10 分钟；
- 加 OpenSpec 约 ¥0.20–0.33，耗时约 9–18 分钟；
- 整个实验 81 个 run，实际扣费 ¥15.30。

具体见汇总表 3。对中小团队来说，**模型费用不是瓶颈，人审规格和设计的时间才是**。选型时应主要比较流程成本，而不是 token 单价。
