# C环节检查发现的问题

## 紧急程度高：授权的时候 用户所在公司 和 授权的公司 不是一个公司时就会触发一个CROSS_COMPANY，但是用户一定有个公司。当我们想要给一个用户A公司的权限和B公司的权限时，一定会被这个判定卡住（用户不能同时属于两个公司），意味着除了超级管理员外的任何用户，乃至超级管理员对单个用户的授权都被限定在一个公司内，这个是不能接受的。必须赶紧修好。

> 处理（10/21）：已修复，登记为 [HR-001](../../findings.md)。取消了 `CROSS_COMPANY`：适用部门可以在用户所属公司以外，公司内角色仍只能指派到本公司；能否授出照常看管理范围（用户所属部门和适用部门都要在操作者范围内）与授权上界。说明见 docs/12 R-20、docs/15 DBG-5，待复核。

## 建议：当前项目不能把用户调到其他公司的部门，但是出于调岗的考虑，确实有可能有让用户修改公司的业务场景，我觉得这个需要设计，建议更新update的鉴权判断。

>

## 需要尽快处理的问题：操作者在AssignmentService里分配某个角色，会调用checkone，checkone会检查合法性，之中会调用escalation检查，escalatio检查操作者有没有这个角色的权限，没有就返回"PRIVILEGE_ESCALATION"导致failure抛出异常。当前设计把“分配权限的资格”建立在“自己拥有这些权限”之上，即，操作者 本人能执行哪些业务操作 和 操作者能向哪些用户、在哪些部门、分配哪些角色 没有解耦。团队认为应该解耦。

## 2026-10-24 补充检查

### 优先处理

1. **P1：最后一个有效 SA 缺少并发保护。** Docker 中通过同步屏障控制真实事务时序，单个自我撤权、批量自我撤权、两个 SA 互相停用三种场景，都复现了两个请求返回 200、最终有效 SA 为 0。`AssignmentService.revoke/batchRevoke` 删除后才普通计数，后面的授权版本锁保护不了前面的判断。建议撤权、停用、删除共用数据库锁，并在锁内读取最新状态、检查剩余人数。**MySQL 实测已复现；并发删除账号尚未单独验证。**

2. **P2：ATOMIC 失败后，PARTIAL 重试丢失目标。** `BatchAssignDialog.submit` 在 `committed=false` 时也触发 `done`，父列表刷新后清空勾选；再点“改为部分执行”，请求的 `targetIds` 变成空数组。建议弹窗保存原目标，重试只改模式，未提交时不刷新列表。**组件测试已复现。**

3. **P2：批量自我撤权不刷新身份。** 单个撤权会调用 `auth.refresh()`，批量操作只通知父页面，导致旧菜单和按钮继续显示。建议批量提交成功后刷新当前身份；按部门、公司展开也可能包含本人。**组件测试已复现。**

4. **P2：新筛选加载时仍能操作旧勾选。** `UserListView.load` 没清空选择，工具栏也未随加载禁用。勾选 A 后搜索其他人，新结果没回来时打开批量弹窗，目标仍是 A。建议筛选、翻页时清空勾选，加载期间禁用相关操作，弹窗和确认框固定目标快照。**组件测试已复现。**

### 编号与批量操作的边界问题

- **内部取号竞争：** 两个不同账号同时取号，实测一个 200、一个 40901，仅新增一条记录；事务回滚正确，但没有自动重试，也没区分取号竞争与用户名重复。若补重试，应只针对取号竞争，在新事务中重新取号。
- **旧库编号：** V3 只抬高自增起点，不修改旧员工的小编号。原项目库升级到 V4 后，实查仍有 28 条 EMPLOYEE 记录的 ID 小于 10000；不能宣称升级后全库都满足分段编号。需要单独迁移历史编号，或明确接受课程旧数据的例外。
- **PARTIAL 并发分配仍会整批失败：** 两批各有一个共同目标、一个独有目标，实测一个 200、一个 409；失败批次的独有目标也未写入，不会自动把共同目标计入 duplicated。
- **批量回收计数失真：** 两个请求同时回收同一指派，实测都返回 200、各报成功 1 人，但实际只删除 1 条。应明确成功人数是“本次实际变更”还是“最终已无指派”。
- **目标口径不一致：** 实测有效用户重复 ID 会去重，无效 ID 重复两次则记两次失败；PARTIAL 遇到不存在的部门直接返回 404，整批不写。需统一或明确统计及失败口径。

### 需要明确的业务规则

- **调岗：** 实测调岗后仍能使用原部门权限，旧指派不会自动迁移或回收。需要明确是否符合调岗预期。
- **停用后启用：** 实测同一个旧令牌在停用时返回 401，重新启用后返回 200，旧指派恢复生效。停用不增加 `tokenVersion`，需明确是暂停使用，还是必须重新登录。删除后指派保留，但重新启用返回 409。

### 已核对的行为

- ID、用户类型、SA 角色没有混用；按当前契约实现，员工可以成为 SA，且不用改类型或编号。但 B 审查记录要求唯一内置 root，两处业务基线需要统一，不能把当前测试通过当成唯一 root 已实现。
- 逻辑删除的内部编号不会复用；内部段达到 9999 后，新增返回 40902。
- Excel 导入员工从 10000 起编号，重复导入不新增；原有 4 项导入集成测试通过。
- 自我撤权免范围检查，但入口仍需撤权权限，与当前契约和页面说明一致。
- 分配检查用户所属部门和适用部门；撤权只检查适用部门，是跨公司授权的既定规则。
- 单个、批量触及最后 SA，实测都返回 409、保留指派、版本号不变，拒绝审计保留；PARTIAL 也整批回滚，但有上述并发漏洞。
- 1000/1001 人实测分别执行 `[1000]`、`[1000,1]` 分块；对第二块注入真实外键错误后，即使 PARTIAL 也返回 409，第一块的 1000 条全部回滚。
- 列表已防旧响应覆盖新响应；详情路由按完整路径重建组件，未发现正常切换直接串错用户的问题。

## 测试脚本补充检查与建议

完整说明见 [测试报告与 RBAC 演进建议](test-report.html)，包含逐脚本结果、17 个 C 责任方法及跨公司关联方法的断言与缺口。

- **执行结果：** 本会话后端集成 52 项通过；本轮前端 42 项、类型检查、浏览器 E2E 9 项通过。原 Redis 初始化脚本执行成功；生成器产生的 11 部门、28 员工、4 功能点与仓库三份夹具内容一致。E2E 只适配启动方式，原业务断言未修改。
- **覆盖率命令失败：** 原 `npm run test:coverage` 行覆盖率为 53.29%，低于 85%，退出码为 1。主要原因是纯类型 `api/types.ts` 被计入 320 行、0 覆盖；仅用 CLI 排除它后，诊断结果为 92.23%，命令通过，仓库配置尚未修改。建议确认纯类型排除规则，保留运行代码门槛。
- **测试缺口：** `api/index.ts` 46 个函数仅 1 个实际被调用；现有覆盖率不统计 views/components。自撤组件用例只看按钮存在，没有执行回收和身份刷新；已有用例也没覆盖上一轮复现的并发、重试及旧勾选问题。应补请求契约与可控异步时序断言，将诊断反例转为会在缺陷存在时失败的正式回归。
- **资料与夹具漂移：** C 清单的 T03 原使用已取消到期功能的旧方法名，部分方法行号过期，本次已同步更正。自撤组件夹具把角色状态写成 `ACTIVE`，真实值应为 `ENABLED/DISABLED`；`roleStatus: string` 没有挡住错误，建议改为字面量联合类型。
- **环境防误用：** 集成基类会 clean/重置数据库、清 Redis，但没有允许清理的 schema 前缀及逻辑库硬校验；E2E 固定用 Redis 5 库，也没有自动删除本次 schema 的 teardown。建议测试启动时校验隔离标志，按运行标识清理，避免并发运行互相清缓存。
