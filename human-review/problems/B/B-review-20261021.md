## 3. 需求与契约基线

### 3.1 权限判定公式

需求 `docs/01-srs.md` 第 242-248 行规定：普通用户只有在账号有效、存在启用角色贡献目标权限、且目标部门为空或落在该条指派作用域内时才允许。超级管理员仅越过权限与部门判断，不越过账号状态。当前主体状态只有不存在、删除、停用，不再包含账号到期。

### 3.2 谁能查谁

`POST /authz/check` 查询本人只需有效登录；查询他人时，调用者必须以 `rbac:authz:invoke` 覆盖被查用户所属部门。`POST /authz/explain` 使用同一主体边界，但要求 `rbac:authz:explain` 并额外返回 `trace`。当前实现不凭 `targetDeptId` 放宽查询他人的资格。

正常完成的权限拒绝是 HTTP 200 + `allowed=false`；调用者无权查询他人才是 HTTP 403。该边界在 SRS、OpenAPI、`AuthzQueryService` 和测试中一致。

### 3.3 下一次访问生效

授权数据变化与 `sys_grant_version.version + 1` 必须处于同一事务。读取时先读 MySQL 版本，再按 `rbac:grants:v<version>:u<userId>` 查 Redis；提交后的请求使用新版本键，旧键即使仍存在也不会再读。

这里的“Redis 键”是 Redis 中定位一项缓存数据的字符串名称，不是密码、JWT 或数据库主键。以 `rbac:grants:v12:u105` 为例，`rbac:grants` 表示授权缓存，`v12` 表示全局授权版本 12，`u105` 表示用户 105；对应的值是该用户的 `GrantSet` JSON。授权变更把版本递增到 13 后，请求改读 `rbac:grants:v13:u105`，版本 12 的旧键不再命中，之后由 TTL 自动清理。

## 4. 完整调用链审核

```text
HTTP 请求
  -> Spring 路由匹配
  -> PermissionInterceptor.preHandle
  -> ContractRoutes 查询 OpenAPI 权限声明
  -> AuthenticationService 验证 JWT
  -> AuthController.check/explain
  -> AuthzQueryService.permissionOf
  -> AuthzQueryService.resolveSubject
  -> AuthorizationService.decide
  -> UserMapper / GrantVersionMapper / GrantCacheMapper
  -> UserRoleMapper / DepartmentMapper
  -> Decision
  -> AuditService.recordDecision(REQUIRES_NEW)
  -> ApiResponse
```

### HR-B-001：角色改名后授权缓存中的展示信息不会立即更新

| 项目 | 内容 |
| --- | --- |
| 类型 | 已确认缺陷 |
| 优先级 | P2 |
| 代码位置 | `RoleManagementService.update` 第 149-177 行；`AuthorizationService.loadGrants` 第 189-204 行；`UserRoleMapper.findGrantsOfUser` 第 40-49 行 |
| 静态证据 | `GrantSet` 缓存的 `AssignmentRow`、`GrantRow` 都含 `roleName`。角色更新仅在 `status` 变化时调用 `bumpGrantVersion()`；只修改 `roleName` 时版本不变 |
| 最小步骤 | 1. 用户完成一次鉴权并缓存旧角色名；2. 管理员仅修改角色名称；3. 用户再次调用 explain 或查询有效权限 |
| 预期 | 下一次读取显示新角色名，解释依据与角色详情一致 |
| 实际推导 | 版本号未变，Redis 命中旧 `GrantSet`，`matched.roleName`、trace 或有效权限来源角色可能继续显示旧名称，最长到 TTL 结束或其他授权变更递增版本 |
| 同页不一致 | 用户详情的 `roles` 每次由 `findAssignmentsOfUser` 实时查库，而 `permissions` 来自可能命中 Redis 的 `GrantSet`；角色改名后角色页签可显示新名称、有效权限页签仍显示旧名称 |
| 权限结论影响 | 不改变 allow/deny，但破坏“权限解释展示实际依据”和同一页面数据一致性 |
| 现有测试 | `roleLifecycleAndPermissions` 只断言改名接口 200，没有先填充授权缓存后核对 explain/用户详情；无对应回归测试 |
| 修复方向 | 已确认角色改名后下一次 explain/用户详情应显示新名称；角色名称变化必须递增授权版本，或调整缓存结构不再保存 roleName，并补缓存已预热场景的回归测试 |

### HR-B-005：成功审计早于外层业务事务最终提交

| 项目 | 内容 |
| --- | --- |
| 类型 | 一致性风险 / 测试缺口，尚未故障注入复现 |
| 优先级 | P2 |
| 代码位置 | `AuditService.record/recordDecision` 使用 `REQUIRES_NEW`；Assignment/Role/Import 等写 Service 在外层 `@Transactional` 中先调用成功审计，外层事务随后才提交 |
| 风险时序 | 业务数据写入和版本 bump 完成 -> `audit.record(...SUCCESS...)` 独立提交 -> 方法返回时外层事务因死锁、连接中断或提交失败回滚 |
| 可能结果 | 数据与版本未提交，但保留一条 SUCCESS 审计，审计不再代表最终业务状态 |
| grant 特殊风险 | `RoleManagementService.grant` 在循环中每新增一个权限就先写一条 `PERMISSION_ASSIGN SUCCESS`，循环结束后才调用 `bumpGrantVersion()`；后续权限保存、bump 或外层提交任一失败，都可能使全部角色权限回滚，但已经独立提交的 SUCCESS 审计仍保留 |
| 现有测试 | 测试覆盖规则拒绝和显式异常回滚后的 DENIED 审计，没有在成功审计后注入外层提交失败 |
| 设计冲突 | “失败回滚仍保留审计”是明确要求，但 SUCCESS 是否允许早于业务提交没有明确规则，需要 F 与各业务负责人确认 |
| 建议 | 先形成规则；如 SUCCESS 必须表示已提交，应考虑 afterCommit 记录、outbox/状态字段，或把提交失败另记 FAILED |

### HR-B-009：`Role.companyId` 公司私有角色无法同时表达总部纵向管理和子公司角色自治

| 项目 | 内容 |
| --- | --- |
| 类型 | 组织模型 / 角色归属 / 管理范围规则待定，定稿前必须选型 |
| 优先级 | P1 设计问题；不同方案影响公司、部门、角色、指派、导入、前端组织树和测试 |
| 已确认需求 | 系统服务一个集团；总公司管理员能够管理全部子公司；子公司管理员只管理本公司；子公司之间横向隔离；超级管理员不承担日常总部管理 |
| 当前主数据模型 | 真实 9 个分公司被建成同一个 `sys_company` 下的 `sys_department` 子树。总公司根 scope 能覆盖这些分公司，但 `Role.companyId` 对所有分公司相同，不能形成分公司独立角色目录 |
| 代码证据 | `Role.companyId=null` 为全局角色、非空为公司内角色；`AssignmentService.checkOne` 限制公司内角色只能落到同公司部门；`scopeOf/inScope` 只比较部门路径；`RoleManagementService.requireCompanyLevel` 规定全局角色只有 SA 能改，公司内角色则要求操作者在该公司根部门持有对应 `rbac:role:*` 权限 |
| 管理规则问题 | 当前“全局角色只有 root/SA 能修改”会阻止拥有集团根 scope 的日常总部管理员维护公共角色；“公司内角色按公司根检查”又无法区分同一 `sys_company` 下的九个分公司。两条规则应与私有角色模型一起重做，不能只修改角色表字段 |
| 核心矛盾 | 当前 9 个子公司都是同一 `sys_company` 下的部门，`Role.companyId` 对它们取值相同，因此“公司私有角色”无法区分子公司；但保留该概念又增加角色可见性、创建、修改和指派规则复杂度 |

#### 方案一：删除公司私有角色

| 项目 | 内容 |
| --- | --- |
| 做法 | 删除或停用 `Role.companyId` 私有归属语义，所有角色都作为集团级角色模板；角色实际在哪些组织生效只由每条 `sys_user_role.scope_dept_id` 决定 |
| 管理规则 | 角色定义由总部管理员统一创建、修改和授权；子公司管理员只能在自身 scope 内把已有角色分配给用户，不能修改角色模板 |
| 代码调整 | 删除公司内角色列表过滤、`ROLE_COMPANY_MISMATCH`、`requireCompanyLevel(companyId)` 和角色表单中的 company 选择；保留全局唯一 `roleCode` 和基于指派 scope 的管理范围检查 |
| 优点 | 模型最简单；符合“集团统一角色、子公司只分配”的集中管理方式；总部根 scope 能覆盖所有分公司部门；避免 company 与部门两套角色归属概念 |
| 缺点 | 子公司不能创建自己的私有角色；所有角色编码和定义都由集团统一管理，角色数量和命名需要中央治理 |
| 适用条件 | 角色模板由集团集中维护，子公司不要求角色定义自治 |

#### 方案二：把公司私有角色改成部门私有角色

| 项目 | 内容 |
| --- | --- |
| 做法 | 用 `owner_dept_id`（名称待定）替代 `Role.companyId`：为空表示集团公共角色，非空表示角色定义归属某个部门节点；子公司根部门可拥有私有角色，总公司根部门可拥有覆盖全集团的角色 |
| 角色管理范围 | 创建、查看、修改角色时，操作者的 `rbac:role:*` scope 必须覆盖 `owner_dept_id`；总部管理员能管理所有下级部门角色，子公司管理员只能管理本子公司根及下级的角色 |
| 指派限制 | 部门私有角色只能指派到 `owner_dept_id` 本身或其下级部门；具体用户获得的实际范围仍由 `sys_user_role.scope_dept_id` 决定，且该 scope 必须落在角色归属部门子树内 |
| 代码调整 | 角色表和 DTO/OpenAPI/UI 将 `companyId` 改为 `ownerDeptId`；列表可见性和 `requireCompanyLevel` 改成部门路径检查；`checkOne` 的公司相等判断改为角色归属路径覆盖指派 scope 路径 |
| 优点 | 与现有总公司—子公司部门树一致；总部纵向管理、子公司横向隔离；允许子公司自定义角色；复用现有 materialized path 和 `Scope` 判定方式 |
| 缺点 | 修改面比方案一大；必须明确公共角色与部门私有角色的编码唯一性、移动部门后的角色归属、总部角色能否下放修改等规则 |
| 适用条件 | 子公司确实需要自行创建和维护角色定义，同时总部仍需管理所有下级角色 |

| 待团队选择 | 方案一适合集团统一角色模板；方案二适合子公司角色自治。当前 review 不代替团队选型，但应删除现有含义不清的 `Role.companyId` 公司私有角色设计 |
| 共同验收条件 | 总部管理员能管理全部角色和用户；子公司管理员只能管理本子公司；兄弟子公司互不可见/不可改；角色指派仍按 `scope_dept_id` 精确控制生效范围；root 不承担日常角色管理 |

## 7. 测试缺口

### 7.1 `selfOnly` 合并缺少直接判定测试

`AuthorizationService.allow` 使用 `candidates.stream().allMatch(GrantRow::selfOnly)`：只有所有覆盖目标部门的候选授权都只限本人时，结果才是 `selfOnly=true`。静态逻辑合理，但现有 B 责任测试没有构造“同一权限、同一目标部门、一条 selfOnly=true、一条 selfOnly=false”的组合并断言 `matched` 与最终 `selfOnly=false`。

### 7.2 缓存与事务交错缺少确定性并发测试

现有 T12/T12b/T22 证明常规撤权、旧键保留和多副本下一次访问，但没有使用锁或屏障构造以下时序：

```text
T1 读取旧版本
T2 修改授权并 bump，尚未提交
T1 查询授权/准备写缓存
T2 提交
T1 写旧版本键
下一次请求读取新版本并拒绝
```

也没有直接测试读写事务中读取未提交授权后回滚，不会留下错误缓存。代码通过 `inReadWriteTransaction()` 禁止写回，设计合理，但证据仍是静态推导。

### 7.3 角色改名、前端乱序和审计提交失败均无回归测试

这三项分别对应 HR-B-001、HR-B-003、HR-B-005。当前覆盖率较高不能替代这些状态/时序断言。

### 7.4 读写事务内“修改授权后再次读取”没有防回归测试

现有 T12/T12b/T22 和 `RedisFailureTest` 覆盖常规缓存命中、撤权后版本变化、旧键保留、多副本与 Redis 故障，但没有构造：

```text
同一读写事务先修改授权
-> 再调用 loadGrants / decide
-> 检查是否读取修改前的 Redis 快照
-> 提交或回滚
```

当前生产代码的授权写入口都在修改前调用 `loadGrants`、`scopeOf`、`isSuperAdmin` 或 `decide` 做管理范围和授权上界检查，修改完成后没有再次读取同一用户授权，因此尚无可到达的已确认缺陷。该项属于未来维护风险和防回归测试缺口：若以后增加事务内写后读流程，应增加专项测试，并考虑在读写事务中同时绕过 Redis 读取。

### 7.5 用户详情测试只断言数量，没有验证语义字段

`ManagementApiTest.userDetailShowsRolesAndEffectivePermissions` 只断言 2 条 roles、3 条 permissions 和 `superAdmin=false`；E2E 只检查页面出现一个角色名、部门名和 `oa` 文本。未验证权限来源角色、scope、selfOnly、同一权限多来源、停用角色仍在 roles 但不在 permissions、停用用户展示语义、角色改名后的同页一致性。该缺口对应 HR-B-001 和 HR-B-013。

### 7.6 停用后重新启用没有验证原角色恢复生效

`ManagementApiTest` 已覆盖 `DISABLED -> ACTIVE` 两个状态接口都返回 200，但没有在停用前预热权限、停用后断言拒绝、重新启用后再断言未回收角色恢复生效。静态代码表明 `applyStatus` 只修改 `sys_user.status`，角色指派和授权缓存均保留；`decide` 下一次请求先读到 ACTIVE，再继续使用原 `GrantSet`，因此原角色会立即恢复。应补完整状态—权限闭环测试。

### 7.7 批量分配/回收缺少版本与审计结果断言

已独立核对 `RoleController`、OpenAPI、`BatchAssignDialog`、`AssignmentService.batchAssign/batchRevoke`、`UserRoleMapper` 批量 SQL，以及 `AcceptanceTest.t16`、`ManagementApiTest` 的批量场景。ATOMIC/PARTIAL、目标展开、重复跳过、分块写入和回收主流程一致，暂未发现新的确定实现缺陷。

现有测试主要断言 `committed/succeeded/duplicated/failed` 和最终权限结果，没有直接断言：实际写入多名用户时授权版本只递增一次；全重复/全跳过时版本不变；ATOMIC 拒绝、PARTIAL 部分成功、完整成功分别产生 `DENIED/FAILED/SUCCESS` 批量审计；外层提交失败后的审计语义。最后一项同时属于 HR-B-005。

## 8. 已确认符合要求的部分

1. OpenAPI 权限声明被运行时读取，未声明路由默认拒绝。
2. `@self` 只负责入口登录校验，“谁能查谁”由 Service 独立判断。
3. 调用者来自 JWT 认证后的 `Operator`，不能由请求体伪造。
4. check/explain 进入同一 `AuthzQueryService.check` 和 `AuthorizationService.decide`，仅 explain 标志不同。
5. `permission` 优先于 `resource+action`，`userId` 优先于 `username`，均与契约一致。
6. 查询别人先检查调用者是否具备查询权限，再处理主体不存在，降低普通用户探测风险。
7. 主体状态每次直接查数据库，不进入授权缓存。
8. 超级管理员旁路位于主体状态检查之后；停用 SA 仍拒绝。
9. 权限和部门作用域保持在同一 `GrantRow`，不会把不同角色/指派拼接成虚假授权。
10. 部门路径采用带尾部 `/` 的物化路径，前缀覆盖判断与导入路径生成方式一致。
11. Redis 只缓存授权数据，正确性由 MySQL 版本号保证；Redis 故障不会继续使用旧权限。
12. 分配、回收、批量、角色状态、角色权限增删和权限导入均能定位到版本递增调用。
13. 版本行更新数量不是 1 时抛异常，使授权修改回滚。
14. 正常权限拒绝返回 200 + `allowed=false`；调用者无权查询他人返回 403。
15. `recordDecision` 区分被判定主体与实际调用者，并记录权限、原因、延迟和缓存命中。

### 8.1 用户状态链审核结论

1. `changeStatus` 和 `delete` 均调用同一个 `applyStatus`，因此范围检查、自己账号保护、超级管理员目标保护和审计口径共用。
2. 已删除用户再次删除或修改时，`applyStatus` 返回 `ALREADY_DELETED`，`statusFailure` 转成 409；现有管理测试已覆盖重复删除 409。
3. 停用账号不需要 `bumpGrantVersion`：用户状态不在 `GrantSet`，`AuthorizationService.decide` 每次在读取授权缓存前直接查询 `sys_user.status`。现有 T03 证明已登录令牌下一次请求 401、再次登录 401、代查结论 `SUBJECT_DISABLED`。
4. 重新启用只把 `status` 改回 ACTIVE，不修改角色指派；未被回收的原角色在下一次请求恢复生效。代码路径明确，但缺少权限闭环测试，见 7.6。
5. 删除是逻辑删除，仅更新用户状态和删除时间，不删除 `sys_user_role`；主审确认保留指派用于审计没有业务影响。删除用户始终在主体状态阶段拒绝，不能使用这些角色。
6. 禁止停用/删除自己是防止管理员自锁和系统失去可操作管理员的保护；需要由另一个有相应 scope 的管理员执行。该规则当前符合安全方向，不列为缺陷。
7. 唯一 root 仍缺少不可删除保护：另一个 SA 可通过共用状态链删除 root，已归入 HR-B-008。
