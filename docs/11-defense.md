## 1. 检查形式（务必全员读懂）

依据《课程设计成绩计算办法》§3.2：

> 检查采用**无领导小组面试**方式，通过课程网站预约检查。在检查前需在课程网站上提交课程设计的详细设计和 Jacoco 测试报告（如无法提供可以提供代码）。
>
> 检查分为**个人陈述**和**自由讨论**两个阶段。个人陈述阶段每位同学依次陈述**文档中的一个设计**。应着重讲清楚以下问题：
>
> 1. 这个设计的**需求是什么，存在什么问题**
> 2. 采用**何种设计方法，采用的理由**是什么
> 3. 展示**实现效果**
>
> 在自由讨论阶段，由其他同学对这个设计进行补充。
>
> 其中**个人成绩和小组成绩各占 50%**。个人成绩来自于每位同学在个人陈述和自由讨论中的表现，小组成绩来自于小组整体的表现，**不会参考小组人数的因素**。

### 关键推论

| 推论 | 说明 |
|---|---|
| **每人必须有一个「自己的」设计** | 陈述的是「文档中的一个设计」，不是「我负责的模块」。因此文档按**设计点**切分，而不是按模块切分——见 §2 的六个设计点 |
| **「采用的理由」是最容易丢分的一问** | 多数人能讲清「我做了什么」，讲不清「为什么这样做而不是那样做」。因此每个设计点都必须准备**备选方案与否决理由** |
| **自由讨论阶段也计分** | 不能只准备自己那一块。每个人都要能对别人的设计提出补充或提问 |
| **小组成绩不参考人数** | 6 人小组和 3 人小组按同一标准评价，人多不是优势，分工不清反而是劣势 |

## 3. 个人陈述讲稿模板

> 按此模板准备，**控制在 5 分钟内**。写成文字稿，检查前演练。

```
【第一步：需求是什么】（约 1 分钟）

这个设计要解决的需求是 ______。
它在需求文档中的编号是 RBAC-REQ-____。
具体来说，用户/系统需要能够 ______。

（如果需求来自老师给的数据，一定要指出来——这证明你读了数据）
例：「权限清单里有 6 个功能点，普通员工那一列写的是『查看本人』。
     这说明仅有功能权限不够，系统必须支持数据范围。」


【第二步：存在什么问题】（约 1 分钟）★最容易被忽略，但很重要

如果用最直接的做法，会遇到这些问题：
  问题一：______
  问题二：______

（要讲具体的失败场景，不要讲抽象的「不够灵活」）
例：「管理员撤销了某角色的 user:delete 权限，但缓存里还有旧数据。
     在缓存过期之前，持有该角色的用户仍然能删除用户。
     这是一个真实的安全漏洞，不是性能问题。」


【第三步：采用何种设计方法，理由是什么】（约 2 分钟）★评分重点

我考虑过这几种方案：
  方案 A：______  → 否决，因为 ______
  方案 B：______  → 否决，因为 ______
  方案 C：______  → 采用

采用方案 C 的理由是：
  1. ______（要结合本项目的具体约束，如读写比 10000:1、数据规模、课程要求）
  2. ______

用到的设计方法/模式是 ______，
如果不用它，会出现 ______ 的问题。

（切忌只说「用了策略模式，因为策略模式扩展性好」——
  要说「不用它的话，新增一类约束要改 3 个已有文件，
  而需求文档 M-1 明确要求不改既有代码」）


【第四步：展示实现效果】（约 1 分钟）

现在演示：______
（打开界面/接口，实际操作，不要只放截图）

可度量的效果：
  - ______（QPS、延迟、覆盖率、改动文件数等具体数字）

（如果有未达标的地方，主动说明，不要等老师问出来）


【预留：可能被追问的问题】

Q: ______
A: ______
```

## 4. 各设计点的「问题」与「备选方案」速查

> 这是讲稿第二、三步的素材库。每个设计点已在对应文档的末节写好，此处汇总便于统一演练。

| 设计点 | 核心「问题」 | 被否决的方案 |
|---|---|---|
| DP-1 | 三份实现若不隔离，范式边界被侵蚀；若完全独立，对比不可信 | ① 单模块分包（隔离不了）<br/>② 三个独立仓库（契约无法共享） |
| DP-2 | 撤销权限后缓存未失效 = 安全漏洞；事务与缓存的先后顺序会导致不一致 | ① 权限写入 JWT（无法撤销）<br/>② 只靠 TTL 过期（窗口期内漏洞）<br/>③ 失效用「更新」（写放大） |
| DP-3 | 角色可多继承（DAG 非树）；配出环会导致计算不终止；只报「有环」无法定位 | ① 树形结构（表达不了多继承）<br/>② 判定时实时遍历（违反性能需求）<br/>③ 写时全量物化（一次变更重算大量行） |
| DP-4 | 结构化的 switch 违反开闭原则；约束若只查直接角色，可经继承绕过 | ① 每类约束一张表（求值流程同构，无必要）<br/>② 约束只作用于直接角色（可被绕过） |
| DP-5 | 前端控制常被误当作安全机制；按钮隐藏使用户无法自助申请；前端缓存权限导致状态不同步 | ① 只做菜单控制（拦不住直接调接口）<br/>② 无权限按钮直接隐藏（用户不知为何消失）<br/>③ 权限存 localStorage（变更后不同步） |
| DP-6 | 权限清单只给功能权限，但「查看本人」隐含数据范围；数据范围后加会全面返工；员工表没有角色列 | ① `data_scope` 挂在角色上（同一角色不同功能点范围可不同）<br/>② 迭代二才加字段（要改 schema、导入、接口）<br/>③ 岗位直接当角色（岗位有几十种，角色只有 5 个） |
| **分级管理**（可并入 DP-2 或 DP-6） | 公司要分公司/部门两级管理员；若新增一套「管理范围」机制，就有两份需保持同步的实现 | ① 新增 `admin_scope` 字段（与 `data_scope` 语义重复）<br/>② 新增 `admin_level` 等级（表达不了「跨分公司但同级」）<br/>③ 同级管理员互改（提权环路） |

## 5. 自由讨论阶段的准备

自由讨论阶段「由其他同学对这个设计进行补充」，**也计入个人成绩**。准备方式：

### 5.1 对其他设计点各准备一条补充

补充的有效形式：

| ✅ 有效 | ❌ 无效 |
|---|---|
| 「这个设计在 ___ 场景下还有一个约束我们讨论过……」 | 「我同意他说的」 |
| 「我们最初的方案是 ___，后来因为 ___ 改成了现在这样」 | 重复别人已经说过的内容 |
| 「这一点和 ___ 这个设计是关联的，因为……」 | 与设计无关的实现细节 |
| 「这里有个已知的局限是 ___，我们的处理是 ___」 | |

### 5.2 已知的「可以主动交代的局限」

主动说出局限，比被老师问出来好得多：

| 局限 | 我们的处理 |
|---|---|
| 结构化实现的缓存失效靠人工保证事务边界 | 如实记录为范式局限，作为对比数据，而非掩盖 |
| 数据范围在迭代一只建字段不执行 | 有意为之：第一次检查范围是 RBAC0，但字段先留好避免返工 |
| 岗位→角色的映射是我们推断的 | 已列入数据疑点 C-10，做成配置表便于调整 |
| 性能指标在课程环境可能达不到 | 如实记录实测值，说明瓶颈与优化方向 |
| 权限清单有 3 处数据缺陷 | 已列入附录 C，导入时归一化并产出异常报告 |
| 安全管理员、审计员是我们增设的角色 | 已说明增设理由（职责分离示范） |
| **只做管理员控制台，普通员工不在本平台登录** | 这是范围决策不是偷懒：员工在各自业务系统登录，那些系统调我们的接口鉴权。管理员验证他人权限用**身份预览**（只读 + 全程审计），比让管理员拿别人账号登录更安全也更可审计 |
| 分级管理没有独立的数据结构 | 有意为之：管理台自身的功能也是受保护功能点，数据范围对其天然适用。新增平行机制才是设计缺陷 |
| 双因素认证未实现 | 老师明确不要求。附录 D 中保留该功能点编号并标注，避免被误认为遗漏 |
| 目标 10000 QPS 远高于实测峰值 400 QPS | 已在 SRS §5.0 给出推算过程与留余量的三条理由。**有依据的余量是设计，没依据的数字是口号** |

## 6. 检查前的检查清单

每次检查前 48 小时逐项确认：

- [ ] 详细设计文档已更新并导出 PDF，提交至课程网站
- [ ] Jacoco 报告已生成，覆盖率达到门槛，已提交
- [ ] 代码在 `main` 分支可一键启动（`docker compose up` 或 `mvn spring-boot:run`）
- [ ] 演示数据已导入，演示脚本（SRS 附录 A-19）**完整跑通一遍**
- [ ] 两种实现的端口都可访问，前端切换功能正常
- [ ] 每个设计点的讲稿已写完并**演练过**，控制在 5 分钟内
- [ ] 对其他设计点各准备了一条补充
- [ ] UML 图已在 StarUML 中重绘，`.mdj` 与导出图已提交
- [ ] 已预约检查时间
- [ ] 断网预案：本地可运行，不依赖外网

> **每次检查前必须完成一次完整的模拟答辩**：按真实顺序每个设计点讲 5 分钟，其余人扮演老师提问。
> 无领导小组面试的形式下，临场表达的分数损失往往比技术缺陷更大。
