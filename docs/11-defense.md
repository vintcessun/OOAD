## 1. 检查形式（务必全员读懂）

依据《课程设计成绩计算办法》§3.2：

> 检查采用**无领导小组面试**方式，通过课程网站预约检查。在检查前需在课程网站上提交课程设计的详细设计和 Jacoco 测试报告（如无法提供可以提供代码）。
>
> 检查分为**个人陈述**和**自由讨论**两个阶段。个人陈述阶段每位同学依次陈述**文档中的一个设计**。应着重讲清楚以下问题：
>
> 1. 这个设计的**需求是什么，存在什么问题**
> 2. 采用**何种设计方法，采用的理由**是什么
> 3. 展示**实现效果**
>
> 在自由讨论阶段，由其他同学对这个设计进行补充。
>
> 其中**个人成绩和小组成绩各占 50%**。个人成绩来自于每位同学在个人陈述和自由讨论中的表现，小组成绩来自于小组整体的表现，**不会参考小组人数的因素**。

### 关键推论

| 推论 | 说明 |
|---|---|
| **每人必须有一个「自己的」设计** | 陈述的是「文档中的一个设计」，不是「我负责的模块」。因此文档按**设计点**切分，而不是按模块切分——见 §2 的六个设计点 |
| **「采用的理由」是最容易丢分的一问** | 多数人能讲清「我做了什么」，讲不清「为什么这样做而不是那样做」。因此每个设计点都必须准备**备选方案与否决理由** |
| **自由讨论阶段也计分** | 不能只准备自己那一块。每个人都要能对别人的设计提出补充或提问 |
| **小组成绩不参考人数** | 6 人小组和 3 人小组按同一标准评价，人多不是优势，分工不清反而是劣势 |

## 4. 各设计点的「问题」与「备选方案」速查

> 讲稿第二、三步的素材库。

| 设计点 | 核心「问题」 | 被否决的方案 |
|---|---|---|
| DP-1 | 一个人属于一个部门，却要在多个部门有不同权限；鉴权、解释、拦截、管理范围四处都要判定，各写一套会结论不一 | ① 只判断权限码集合（做不了部门，审查发现的 P0）<br/>② 权限码集合 + 部门集合分别判断（拼出不存在的授权，T07b）<br/>③ 解释接口另写一套判定（两套逻辑会矛盾） |
| DP-2 | 撤销权限后缓存未失效 = 安全漏洞；多副本时只清本实例的缓存不够；删键与正在回填的请求有竞争 | ① 权限写进 JWT（过期前收不回）<br/>② 只靠 TTL 过期（窗口期内漏洞）<br/>③ 本地缓存 + Pub/Sub + 轮询（最终一致，不是「下一次访问」）<br/>④ 变更后逐个删键（回填竞争会写回旧数据）<br/>⑤ 不用缓存（需求要求提供缓存设计）<br/>⑥ 版本号放 Redis、事务提交后 INCR（INCR 失败时库已改、版本号没变，旧授权在 TTL 内继续生效，[12 #37](12-design-log.md)） |
| DP-3 | 有「分配角色」权限不等于能给任何人、在任何部门、分配任何角色；管理员可以给下属授予超出自己的权限再借账号越权；回收管理员时会不会连带回收 | ① 只在拦截器判断「能不能分配」（拦不住越界）<br/>② 靠前端组织树的可见范围限制（后端可直接调用）<br/>③ 另建一套管理员等级（与部门树重复）<br/>④ 按 `granted_by` 级联回收（违反需求）<br/>⑤ 授权上界只比权限码与部门（「查看本人」可以授出完整「查看」，[12 #36](12-design-log.md)） |
| DP-4 | 1,000 人里 3 人不合规怎么办；员工表的「财务部」在 10 个地方都有；岗位不等于角色 | ① 逐人调用单个分配接口（无整体语义、慢）<br/>② 默认部分成功（管理员误以为全体已授权）<br/>③ 按部门名匹配（错配）<br/>④ 导入时按岗位自动派生角色（违反人工分配） |
| DP-5 | 每个 Controller 手写权限判断容易遗漏；契约写了不等于实现了；隐藏菜单常被误当成安全机制 | ① 注解散落在 Controller（无法统一核对）<br/>② 只做单向核对（漏掉未实现的接口）<br/>③ 只做菜单控制（拦不住直接调接口） |
| DP-6 | 两家公司都有「财务部」；部门层级与角色层级容易混淆；没有外键会留下孤立授权 | ① 部门名全局唯一（放不下多公司）<br/>② 多个根节点模拟多公司（说不清人和角色属于哪家）<br/>③ 部门挂在角色上（同一角色不同部门要建多个角色）<br/>④ 不建外键（需求没有高并发要求，理由不成立） |

### 高频追问：「为什么不在登录时鉴权一次？」

> 登录做的是**认证**——确认你是谁，一次就够。**授权**每次都做，因为：第一，需求要求权限修改后下一次访问就生效，登录时下发的权限在令牌过期前收不回来；第二，能不能操作取决于目标数据在哪个部门，登录时不知道。每次判定先查 Redis 里的授权缓存，不必每次查库；令牌只证明身份，不带权限。

详见 `02-architecture.md` §4.3、§4.6。

### 高频追问：「所有接口都做了权限控制吗？怎么保证没有漏？」

> 每个接口在 OpenAPI 契约里声明所需权限，拦截器按契约统一拦截。只有登录免登录；「查看本人」这类接口声明为 `@self`，能看谁由 Service 判断。**契约里查不到的路由一律拒绝**，所以漏配的后果是「谁都调不通」而不是「谁都能调」。启动时双向核对：代码有而契约没声明、契约有而代码没实现，任何一边不一致都拒绝启动。

详见 `04-api.md` §1.4。

### 高频追问：「为什么设了超级管理员旁路？」

> 需求要求「越过权限引擎」。旁路排在账号状态校验之后，停用的超级管理员照样被拒（T11）；每次放行都记审计，原因写明 `SUPER_ADMIN_BYPASS`；超级管理员角色只有超级管理员能分配和回收，不能回收最后一个。

### 高频追问：「为什么有部门树，却没有角色树？」

> 组织树决定人员属于哪里、管理员能管到哪里；RBAC0 的角色只决定权限集合。需求明确只做 RBAC0、不做 RBAC1，所以角色没有继承。部门树是组织信息，不是角色继承。

### 高频追问：「角色为什么不带部门？」

> 角色只回答「有哪些权限」，「在哪个部门范围内行使」挂在每一次指派上（`sys_user_role.scope_dept_id`）。如果角色带部门，同一组权限要按 111 个部门复制成 111 个角色，权限一改就要改 111 处。现在同一个角色可以指派到任意部门，一个人也可以在不同部门持有不同角色，而且作用域逐条跟着指派判断（T07b）。`sys_role.company_id` 只表示「这是某家公司私有的角色」。

详见 `03-database.md` §4.6。

### 高频追问：「管理员能撤销自己的权限吗？撤销后怎么办？」

> 能。回收自己的指派不检查管理范围，因为放弃权限不会扩大任何人的能力；授权上界管的是授出，不是放弃。撤销管理员角色后，下一次请求就没有管理能力（T14b），要恢复只能由其他管理员重新分配。唯一的例外是最后一个有效的超级管理员不能撤销自己，否则系统就没人能管了（409）。每次撤销都记 `ROLE_REVOKE`，操作人和对象是同一个人。

### 高频追问：「用户编号为什么要分段？」

> 课堂要求预留一段编号给内部用户。1–9999 是内部账号：`root` 是 1，业务系统账号依次往后编；员工和临时用户从 10000 开始，一万名员工导入后也不会占到内部段。好处是一眼能区分「这是系统账号还是人」，以后加内置账号不用挪别人的编号。实现上员工走数据库自增（V3 把起点设为 10000），内部账号由服务层在段内显式取号；MySQL 的 CHECK 约束不能引用自增列，所以由服务层保证，并有测试覆盖。

### 高频追问：「所有操作都有日志吗？日志分级吗？」

> 改变数据的操作，成功、被规则拦下都有记录；登录、改口令失败也有。越界统一在 `requireInScope` 一处记 `ACCESS_DENIED`，带上需要的权限码。有意不记的有三类：输入格式错误、对象不存在、重复提交，这些不是安全事件；`@self` 接口只读自己的数据，没有发生权限判定；没带令牌的请求还不知道是谁。查询接口记的是「能不能调」，不记返回了哪些数据。审计没有单独的级别列，`event_type`、`result`、`reason` 三列已经能筛，Dashboard 的「异常访问」就是按这三列定义的一级。口径表在 `06` §5.9。

### 高频追问：「一个人能拿到两家公司的权限吗？」

> 能（10/21 起）。用户只属于一家公司，但指派的适用部门可以在另一家公司：给他两条指派，适用部门分属两家公司，鉴权时各自只覆盖对应的部门子树，不会串到对方的同名部门（T19）。谁能这样授权照常看管理范围：用户所属部门和适用部门都要在操作者的范围内，所以只管一家公司的管理员不行，超级管理员或持有两家公司管理指派的管理员可以。回收则管得到其一即可：A 公司能收回别人在自己部门的权限，B 公司也能收回本公司员工的权限；A 公司的业务系统也能按目标部门判定这个人在 A 的权限。公司内角色仍只能指派到本公司。原来的规则是「适用部门必须与用户同公司」，要跨公司就另建账号，组内审查认为这会把每个人锁死在一家公司、同一个人两个身份，已取消（12 R-20）。

### 高频追问：「三台服务器就叫分布式？」

> 多个服务用 Swarm 部署在不同节点，但数据节点和应用节点各只有一个，存在单点，我们不把它称为高可用集群。需求明确不做高并发专项设计，所以没有做数据库主从、Redis 哨兵。

## 5. 自由讨论阶段的准备

自由讨论阶段「由其他同学对这个设计进行补充」，**也计入个人成绩**。准备方式：

### 5.1 对其他设计点各准备一条补充

补充的有效形式：

| ✅ 有效 | ❌ 无效 |
|---|---|
| 「这个设计在 ___ 场景下还有一个约束我们讨论过……」 | 「我同意他说的」 |
| 「我们最初的方案是 ___，后来因为 ___ 改成了现在这样」 | 重复别人已经说过的内容 |
| 「这一点和 ___ 这个设计是关联的，因为……」 | 与设计无关的实现细节 |
| 「这里有个已知的局限是 ___，我们的处理是 ___」 | |

### 5.2 已知的「可以主动交代的局限」

| 局限 | 我们的处理 |
|---|---|
| 前端只覆盖管理控制台 | 员工在各自业务系统里使用权限，那些系统调 `/authz/check`；控制台面向管理员，普通员工登录只看到个人中心 |
| 「查看本人」类权限 RBAC0 不做行级过滤 | 鉴权结果带 `selfOnly`，由业务系统按记录归属过滤；外部模拟系统的考勤接口就是这样做的 |
| 资源编码按出现顺序编号（如 `oa:m01:f02`） | 原表只有中文名；系统码用固定对照表，模块、功能点首次导入时按顺序编号。重复导入按「模块 + 名称」认领已有功能点，清单中间删行、插行不会让编码错位 |
| 2 个部门负责人重名，没有自动关联 | 不猜，进异常清单，由管理员确认；负责人关联本来就不产生权限 |
| 授权缓存的失效是全局的（任何变更都让所有人的缓存失效） | 需求不做高并发设计；换来的是简单且可证明正确。变更远少于鉴权 |
| Redis 故障时 | 授权缓存当作未命中、直接查库，结论不变；令牌注销查询失败按已注销处理，宁可重新登录 |
| 三节点不是高可用 | 如实说明，见上 |
