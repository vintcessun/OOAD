== 可重复生成与失效规则

[source,shell]
----
# 在仓库根目录；JDK 21 的 javap/java 在 PATH，或设置 JAVA_HOME
python tools/render-rbac1-design.py
# 按 Java 源码局部重画两张包图，先在 rbac-web 安装项目依赖和 Playwright Chromium
python tools/render-rbac1-design.py --packages-only
# 业务代码稳定并编译三模块之后，要求编译产物不旧于源码
python tools/render-rbac1-design.py --strict-compiled
# 发布前检测源码/DDL/部署定义与图快照是否一致
python tools/render-rbac1-design.py --check
# 绘图器自身回归
python tools/render-rbac1-design.test.py
----

全量生成依赖 Python 标准库、Graphviz `dot`、JDK 与 `rbac-web` 现有的 Playwright Chromium。包图生成使用 Python 输出 SVG，由 Chromium 导出同尺寸 PNG。首次准备浏览器时，在 `rbac-web` 运行 `npm ci` 和 `npx playwright install chromium`。PlantUML 固定为 1.2025.2，首次从 Maven Central 下载到系统临时目录，实际 jar SHA-256 写入索引。
`--strict-compiled` 缺类或源码新于 class 时写出 `PENDING_COMPILE` 并失败，不伪造生成成功；普通模式只允许源码快照，显式记录待编译。生成时检查类、字段 role 和方法声明，编译产物当前时再检查 javap；源码在生成期间改变则失败。

顺序图的维护源集中在 `tools/render-rbac1-design.scenarios.py`，与渲染引擎一起纳入失效检查；不要只改生成后的 puml。`--check` 同时检查新增 Java 文件、class 字节哈希、图文件哈希及部署输入变化。重载方法在索引保留全部 javap 候选签名，实际接收者与参数类型还要回到调用方法体核对。

类图使用三段框、Service 中心罗盘布局；字段关联标真实 role，局部/参数依赖不写文字，Adapter 的实现箭头指向端口接口。脚本检查类框重叠及直线穿第三方类框；这是几何检查，不证明 UML 语义或源码调用分支正确。
顺序图是重要调用的投影，不是每条 SQL 的执行 trace；参数是源码中的上下文表达式，完整参数和返回类型由索引/类图核对。图中文字中的异常码指源码抛出的内部领域/业务码，最终外部错误封装还由当前 Advice/ExceptionHandler 翻译，统一错误码修改后必须检查该边界。事务管理器的提交用 note/group 描述，不捏造业务 `commit()` 方法。

=== 跨平台哈希规则

SHA-256 对清单内源码/配置等文本仅做字节级 CRLF→LF 后计算；不去 BOM、不 trim、不改独立 CR、不折叠空白或重编码。文本扩展名与特殊文件名白名单在 source-index.json / verification.json 的 hashRules 明示；Java、Python、SQL、YAML、JSON、XML、adoc、图源/SVG 等属于文本。其余文件按原始字节，尤其 .class / .jar / .png 绝不归一化。因此 Windows 工作树 CRLF 与 Git/CI LF 的同文不会误报，二进制变化仍会报错；原有符号、javap、role 和调用顺序门禁未放宽。19 项工具回归保留原 7 项（含文本/二进制两项，独立 CR、空白、BOM 不得被抹去），另有 12 项显式证据模式正反例：默认 current 严格拒绝不匹配/缺失 JAR，archived 验证历史两轮且不能升级为当前部署/业务验收，缺失或损坏归档必须失败。

修改业务规则后必须同时检查：调用归属、控制片段、事务传播、错误码、图源与正文；仅重跑渲染不能自动推导新的控制流。结构化 Controller 方法名由实际 `management.<method>` 调用反查，因此不能为图好看把真实方法改名。

== 当前职责与依赖方向

=== 结构化：事务脚本与数据访问

image::structured-packages.svg[结构化包图]

`controller.ManagementController` / `AuthController` 适配 HTTP；`PermissionInterceptor` 获取身份、登记路由权限；`service.ManagementService` 以 `begin → 校验/改变 → finish` 管理命令事务。
`AuthorizationService` 内聚图遍历、授权上界、管理范围与缓存过程，`AuditService` 负责同步审计和幂等事务。
`mapper.Store` 封装 EntityManager 查询、分页、保存及悲观锁；`entity.*` 是数据记录，不将其宣称为有行为的领域聚合。

=== DDD：应用编排、领域规则、仓储端口

image::ddd-packages.svg[DDD 包图]

`interfaces.rest` 适配请求；`application` 管锁、认证授权协调、加载、保存及同步审计；`domain` 保存 `Role`、`User`、`RoleHierarchy`、`DepartmentEligibility`、`AuthorizationPolicy`、`AuditFact` 的实际行为。
`domain.port.AuthorizationRepository` 等是面向领域/用例的端口，不是 JpaRepository；`infrastructure.persistence.Jpa*RepositoryAdapter` 实现这些接口并操作 `*Entity`。
应用服务不应依赖具体 JpaAdapter。图中的实现关系为 Adapter → Repository，不画反。

两张图沿用课程项目原始 SVG 的系统字体栈、浅灰底、分区色条、文件夹包框与图例。灰色虚线空心箭头表示主要依赖，蓝色虚线搭配空心三角表示包内类型实现了目标包中的端口。箭头均指向被依赖或被实现的一方。绘图范围是 `rbac-structured` 与 `rbac-ddd` 各自的主要 Java 子包，跨模块关系见 link:../diagrams/phase2/src/architecture-modules.mmd[模块架构图源]。图的 SVG 保留原项目的 MIT 许可说明。布局参照 link:https://gitee.com/mingqcn/course-project-mgt/blob/990cea2cc3686599ef5068945706a13e7e0afc5b/docs/backend-design.md[课程项目后端设计第 17.1、17.2 节]。

结构化图保留 `service → mapper` 和 `service → entity` 两条依赖，分别对应事务脚本使用 `Store` 和直接处理数据实体。`dto → entity` 表示将请求输入映射到实体，角色、部门和用户的响应字段由 `service.Views` 组装。`config → controller` 对应 `WebConfig` 注册 `PermissionInterceptor`。

DDD 图中的 `interfaces.rest → interfaces.rest.dto` 来自 REST 层对 DTO 的全限定类型引用。`interfaces.rest.dto → application` 对应 `CreateRoleRequest` 向 `RoleCommand` 的映射及 `RoleView` 从 `RoleResult` 的转换。`infrastructure.persistence → infrastructure.persistence.repository` 对应 `JpaAuthorizationRepositoryAdapter` 调用的三个 JPA Repository。仓储、身份、缓存和操作契约实现分别由 `infrastructure.persistence`、`infrastructure.identity`、`infrastructure.cache` 和 `infrastructure.config` 指向 `domain.port`。

维护文件包括 link:../tools/render-rbac1-design.packages.py[RBAC1 包、关系与坐标] 和 link:../tools/render-rbac1-design.package-template.svg[改自课程项目的 SVG 模板]。生成时核对代表类型的包名、所选依赖的 import 或全限定类型引用，以及实现箭头对应的 `implements` 声明。包图用于阅读所选关系，全面的架构约束仍由项目测试校验。

== 物理模型与继承方向

image::schema-15-er.svg[当前十五表]

ER 从共享 `rbac-contract/src/main/resources/db/migration/V1__rbac1_schema.sql` 生成，恰为十五表。列、唯一键、CHECK、索引及完整 DDL 行见 link:design/schema-constraints.json[约束索引]。

* `sys_system`、`sys_department`、`sys_user`：单公司、单一部门归属，部门 parent 自引用；部门允许角色不是角色权限。
* `sys_role`、`sys_permission`、`sys_role_permission`：角色属于系统，权限按 UI/API 区分；桥表唯一键避免重复。
* `sys_user_role`、`sys_department_allowed_role`：直接指派与部门准入独立表达，指派者 `assigned_by` 是用户外键。
* `sys_role_hierarchy`：`senior_role_id → junior_role_id`；DB 防自环和重复，但一般环和跨系统仍靠持锁业务规则。
* `sys_ui_resource`、`sys_api_operation`、`sys_ui_api_mapping`：UI 与 API 显式映射，不从路径或菜单可见性推导 API 放行。
* `sys_token_revocation`、`sys_grant_version`：令牌撤销事实与全局授权版本；Redis 不是权威。
* `sys_audit_log`：request_id 唯一，保存 actor 快照、来源、payload_hash、结果。DDL 没有 actor 外键；ER 不凭空画它，删除用户后历史仍能解释。

image::role-senior-junior-dag.svg[继承语义例而非实际数据库截图]

A→B 表示 A 继承 B，权限沿 senior 到 junior 合并；多父、菱形合法。停用节点切断经过该节点的路径，不切断其他合法路径。图是语义夹具，不声称数据库当前存在 A/B/C/D。

每个 S 编号在图索引中有两版 `*-class` / `*-sequence`。S04 两张类图保留独立网关的历史结构，主顺序图分别展示当前 Compose 两版的中心内嵌代理与授权调用。

=== S01：并发、锁与失败

image::S01-structured-sequence.svg[结构化继承]
image::S01-ddd-sequence.svg[DDD 继承]

结构化 `begin` 先 `AuthorizationService.lock` 锁单行 GrantVersion；DDD `lockGrants` 亦在读写授权事实之前执行。自环、跨系统、环、重复边拒绝；授权上界验证后才能保存并成功审计。加锁错误、DB 错误和未捕获业务异常使外层事务回滚。图不声称并发测试已通过。

=== S02：资格不等于权限

image::S02-structured-sequence.svg[结构化指派]
image::S02-ddd-sequence.svg[DDD 指派]

DDD JpaDirectoryRepositoryAdapter.saveUser 在首次 INSERT 之前直接生成最终 `rbac-` + UUID 的不透明 subject，不再先写临时 subject 再 UPDATE 消耗一次乐观版本。调用顺序门禁也要求 subject 只赋值一次且 UUID 在 persist 之前；不把这种技术修复画成新的领域业务规则。

部门可指派集合只约束直接赋予角色；不把部门角色自动算作用户权限。管理范围是 actorPath/targetPath 的边界，提权上界是另一个边界；前端禁用按钮不替代任一检查。

image::department-state.svg[部门状态与新接纳]

指派流程先检查部门是否接受新指派。停用的非根叶部门保留已有成员及授权，关停新接纳，并从课程目录隐藏。用户恢复检查的是保留角色实际恢复的权限及身份标记。跨部门调动会清空该用户全部直接指派。

=== S03：查询也有规则

image::S03-structured-sequence.svg[结构化权限]
image::S03-ddd-sequence.svg[DDD 权限]

两版用户详情先校验调用者的查看权限，再确认目标系统存在，之后才读取目标用户并检查部门范围。系统编码不存在时统一返回 `404 SYSTEM_NOT_FOUND`，响应与目标用户是否存在无关。通过范围检查后，目标系统或目标用户已停用时返回 `200` 和空权限。

Structured 的 S03 HTTP 查询在只读事务内运行。目标启用时计算权限快照，目标停用时使用空快照，再由 `AuthorizationService.effective` 转换为接口响应。图中分隔线下方独立展示 `snapshot()` 在其他调用中无事务时的缓存与重试过程。

有效权限以数据库的版本和状态为准，事务中不读写授权缓存。DDD `stableEffective` 先读版本，再检查目标系统和目标用户。目录服务把目标系统的 `SYSTEM_DISABLED` 转为空有效权限。无实际事务且目标用户 ACTIVE 时才可 cache.get/put。写入缓存前和写入后均复查授权版本，版本变化就重试，三次仍不稳定返回 `503 AUTHORIZATION_UNSTABLE`。

若当前实际事务为只读，`effective/api` 通过独立 Spring Bean `AuthorizationReadTransaction.fresh`，在 REQUIRES_NEW、READ_COMMITTED、readOnly 事务执行 Supplier 回调；`stableEffective/stableApi` 每次尝试先 `repository.freshenRead`，JpaAdapter 用 EntityManager.clear 清理持久化上下文。写事务不另开读取事务，避免把尚未提交的授权变更误读成旧事实。图中回调分支注明相同算法，普通分支展开循环；不能把 fresh 简化成“清一次缓存”。

结构化 `snapshot` 的三参数构造器保留默认值兼容，Spring 注入的四参数构造器读 `rbac.cache.namespace` 并拒绝空白。实际键为 `namespace:authz:system:user:version`。事务外每轮先读取版本，再校验用户和系统状态，在 L1/Redis 写入前后复查版本。事务内直接计算。两个独立数据库需要使用不同的 namespace。结构化上界在 `begin → captureUpper` 于变更前冻结 actor 快照，防止自修改后用新权限证明新权限。

=== 管理端停用目标模拟：与实际授权状态修改分开

image::SIM-ddd-class.svg[目标可用性检查类图]
image::SIM-ddd-sequence.svg[管理端模拟判定和解释]

`AuthorizationController` 的 `check` 和 `explain` 都通过私有 `check` 校验调用者。代查他人时还会检查目标部门范围。两种入口的 UI 和 API 模拟都调用 `simulate`。每轮读取授权版本、目标状态、权限快照和判定，再复查版本。UI 判定匹配快照中的权限码，API 判定检查登记的操作策略。版本变化时重做整轮，稳定的未知目标返回 404。停用用户或系统的模拟返回 `allowed=false` 及 `USER_DISABLED` 或 `SYSTEM_DISABLED`，`explain` 同时带上空权限和对应的解释轨迹。共享验收场景使用 SIM 图，UML-S06 顺序图展示同步成功审计。

=== S04：可信 operationId 与双层鉴权

image::S04-structured-sequence.svg[Structured 中心内嵌课程代理]
image::S04-ddd-sequence.svg[DDD 中心内嵌课程代理]

当前 Compose 由课程前端的 Nginx 将受保护的 `/api/` 路由交给 `rbac-backend`。`course.upstream` 启用 `CourseProxyFilter`，它以方法与路径匹配可信 `operationId`，通过后端本地回调校验令牌、课程 audience 和 API 权限。允许后才限量读取请求体，再由 `ProxyClient` 发往课程后端。课程后端的对象级 403 由代理保留。外部审计另走课程后端向中心的同步 HTTP 调用。link:../deploy/full-course-nginx.conf[课程 Nginx] · link:../docker-compose.yml[默认 Compose] · link:../rbac-course-proxy/src/main/java/com/xmu/rbac/gateway/CourseProxyFilter.java[代理入口]

历史独立网关使用 `GatewayController → AuthBoundary → IdentityClient` 跨服务调用中心 API 判定，再由 `ProxyClient` 转发。这个结构保留在 S04 两张历史类图中，相关接口边界仍可单独阅读。

image::S04-ddd-policy-sequence.svg[DDD 版本一致的 API 决策]

`stableApi` 用版本括号包住 operation 策略读取、目标身份、effective 计算、目标身份再次读取以及 allows；尾部版本不同重试，至多三次后 503。不能仅保证权限集合新鲜却使用旧 operation.enabled 或旧身份状态。`validate` 将未知 aud 引起的系统查询 404 转成 401 TOKEN_INVALID；真正不存在的 operation 仍是 API_OPERATION_NOT_FOUND，不能混同。

=== S05：幂等并不等于先查后插

image::S05-structured-sequence.svg[结构化审计]
image::S05-ddd-sequence.svg[DDD 审计]

Actor 由已验证 token 与服务端状态派生，外部还要服务密钥与 audit:write。先白名单 JSON、规范化再算摘要；DB request_id 唯一。DDD AuditFact 的紧凑构造器将 at 截到 MILLIS，结构化 AuditService.record 也截毫秒，确保 POST 返回、TIMESTAMP(3) 持久化、重放响应与闭区间 [at,at] 查询一致。结构化 AuditLog.requestId 显式 columnDefinition=char(36)，GrantVersion.id 的 Java Long 显式映射 tinyint；不能因为 Java 类型是 Long 就画成物理 BIGINT。已提交但网络超时只能重试原 requestId。中心接收方幂等不保证课程调用方自动可靠重试；若调用方丢失原 requestId 或不重试，不能宣称两系统审计强可靠。没有分布式原子事务，也不增加 Outbox、MQ、异步消费者。

=== S06：成功与拒绝是不同事实

image::S06-structured-sequence.svg[结构化同事务]
image::S06-ddd-sequence.svg[DDD 同事务]

`success/local` 加入本地业务事务，审计失败不能返回业务成功；提交发生在事务代理返回 Controller 之前。DDD `complete/done` 先由 GrantIntegrityService 读取当前已变更的图、权限与 active identities，交 LastAdministratorPolicy.requireAvailable 保护至少一个有效超级管理员，再推进版本、同步审计。`local` 不再构造空角色假快照，而从当前 actor 的有效受控身份角色派生快照；系统查无结果的 404 可按源码降为无角色，其他领域异常不能吞掉。独立 `denied` 使用 REQUIRES_NEW，保存 DENIED 而非 SUCCESS；它是否被实际拒绝入口调用，要按拦截器/Advice 源码检查，不能只因方法存在就断言所有拒绝都已落库。
LayerLoggingAspect 的层级、耗时、异常类型属于技术运行日志；即使出现“方法返回”日志，也不能证明 DB commit，更不能替代 audit_log 的业务事实记录。

== Role 状态与对象不变量

image::role-state.svg[真实 Role 状态图]

`Role.changeStatus(boolean)` 当前是状态赋值，允许同状态重复设置；不捏造“已启用禁止再启用”规则。Role 构造保护 system/code/name 非 null 和受控 identityRole；rename 不允许空白 name；replacePermissions 拒绝跨系统权限。`Role.superAdministratorCapability` 以 rbac-center / SUPER_ADMIN 判断特殊能力，`requireManageable` 要求 actor 具超级管理员资格才可管理它；该能力不因当前停用或权限集合为空就变成普通角色。`RoleHierarchy.requireGrantable` 检查向该能力的可达性时不切断停用节点，防止预埋继承路径；AuthorizationPolicy.requireWithin 同时拒绝非特权 actor 的直接/有效 SUPER_ADMIN 能力。系统启停、最后超级管理员和启用后的授权上界仍是应用/跨对象规则，不虚称 Role 单独保护全部规则。
`RoleHierarchy.link` 保护同系统、无环、不重复；`User.assign` 保护 ACTIVE、部门一致、资格和重复；`DepartmentEligibility.retained` 做集合交集；`AuditFact` 保护 requestId/target、快照不可变及重放一致性。

最新代码还包含真实 PATCH 边界：RoleController.patch 的 RoleUpdateRequest → RoleUpdateCommand，DirectoryController.patchUser 的 UserUpdateRequest → UserUpdateCommand，以及 ResourceController.ui/uiPatch 的 UiChangeRequest → UiChangeCommand，均用 copy；字段 presence 单独传入应用服务，区分“未提供”与“明确 null 清空”，不能换成全量 copyNotNull。ResourceViews.ui 显式构造 children，并将它作为模板字段传给 UiResourceView 的 record 映射。JpaResourceRepositoryAdapter 通过 UiState 与 UiResourceEntity 之间的复制转移字段，树规则由业务用例处理。

Controller 成功封装现在明确保留 `data:null`，不因 Map.of 禁止 null 而抛异常。共同的 rbac-contract.ApiErrors 只统一 HTTP status/code/中文 message 词汇，由 REST Advice/Handler 调用；它没有鉴权、图算法或事务，不是跨实现共享业务 Service，领域内部原因可保持独立。模拟目标的 USER_DISABLED 是返回结果的 reason，不应被普通认证错误封装替换。

CloneFactory 是编译时生成的字段映射，不是严格 GoF Factory Method，也不能代替 DFS、资格判断、权限并集或安全审计白名单。工具不代替注解处理器的 clean build 测试；新增同名敏感字段必须重新检查生成代码和反向拷贝。静态 copy 若进一步补入顺序图，应使用 «MetaClass» lifeline，而非普通实例。

== GRASP 与工程取舍

* Information Expert：RoleHierarchy 知道边与路径，User 知道部门与直接指派，AuthorizationPolicy 知道权限合并/上界，AuditFact 知道自己的重放键与摘要语义。
* Controller：ApplicationService 是 GRASP 用例协调者；REST Controller 是协议适配，不等同于所有业务规则的拥有者。
* Creator：领域合法构造与应用装载后调用真实对象行为；不为了模式名添加无意义 Factory。
* Low Coupling / Indirection：Repository 端口隔离 JPA，`CourseProxyFilter.Authorize` 接收当前后端的鉴权回调，`ProxyClient` 负责到课程后端的 HTTP 传输。
* High Cohesion：图规则不混进 HTTP/SQL；审计协调不混进课程业务；技术日志不充当审计领域对象。
* Pure Fabrication：Store/JpaAdapter/RestSupport 承担查询、映射等技术职责。不是把所有领域算法搬入通用工具类。

结构化优势是命令流程集中、简单 CRUD 修改路径短；代价是管理 Service 承担多类不变量，测试通常需要更多存储上下文。DDD 使图、资格和权限规则可以脱离框架测试，但增加端口、装配和对象转换成本。不能据此直接声称 DDD 性能更好、文件更少或两版测试已等价。需用实际新规则修改范围和共享黑盒结果说明，而非伪造 Git diff。

== 持久登录锁：先提交失败事实，再对外 401

image::LOGIN-ddd-class.svg[持久登录锁职责]
image::LOGIN-ddd-sequence.svg[持久登录锁事务]

真实链为 IdentityApplicationService.login → LoginAttemptApplicationService.attempt。attempt 在事务内 `lockLogin` 串行化账号行，LoginAttemptPolicy.locked/evaluate 判断；仅 ACTIVE 且未锁才做密码匹配。第 5 次错误锁 900 秒；锁定中不继续累加，过期重新计数，正确凭据清零。`saveLoginState` 与 LOGIN_DENIED 同事务，失败时返回 null，事务正常提交后外层 login 才抛 401，避免安全计数被同一个异常回滚。不存在账号返回 null；系统停用/审计持久化异常仍使 attempt 事务回滚，不能笼统说“任何登录失败都已提交计数”。
