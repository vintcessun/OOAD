# 设计问题与改正记录

> 第二次检查（11 月底）要求能回答「**设计问题和改正的理由**」。本文档记录设计过程中发现的每一个问题：发现了什么、为什么错、怎么改、为什么这样改。
>
> **规则**：凡是改了设计，就在这里追加一条，不删除旧条目。条目编号不复用。

---

## 条目格式

| 字段 | 内容 |
|---|---|
| 发现时间 | 日期与所处阶段 |
| 问题 | 原来的设计是什么 |
| 为什么错 | 会导致什么后果，给出具体的触发场景 |
| 改正 | 现在的设计是什么 |
| 理由 | 为什么选这个改法，而不是别的改法 |
| 影响范围 | 改了哪些文档、表、接口 |

## #1 互斥角色演示对在引入继承后不可满足

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-20，设计 V3 约束脚本时 |
| 问题 | 静态互斥（SSD）的演示规则选的是「普通员工 ⟂ 部门经理」 |
| 为什么错 | 迭代二引入角色继承后，部门经理继承普通员工。约束作用于**有效角色**（A-21），所以每个部门经理都同时有效持有两个角色，**全部违反约束**——这条规则不可能被满足。迭代一不会暴露，到迭代二才会炸 |
| 改正 | 演示对改为「审计员 ⟂ 系统管理员」；并新增规则：创建 SSD 约束时校验规则内任意两角色在继承图上不得互为祖先，违反返回 `24005 CONSTRAINT_INEFFECTIVE` |
| 理由 | 只换演示数据治标不治本，管理员以后仍可能配出同样的无效规则。在写路径上校验，把错误挡在配置阶段。审计员与系统管理员的互斥也有真实的业务含义：审计员监督系统管理员，两者合一则审计失去独立性 |
| 影响范围 | `V3__rbac2_constraints.sql`、`rbac-api.yaml`（错误码 24005）、SRS CSTR-001 |

## #2 数据导入步骤顺序颠倒

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-20，复查导入设计时 |
| 问题 | 导入流程中「按岗位派生用户角色」排在「绑定部门经理」之前 |
| 为什么错 | 岗位→角色的配置规则中，优先级 2、3 通过 `sys_department.manager_user_id` 判断「此人是否为部门经理」。派生先执行时该字段还是空的，**所有部门经理与项目经理都会被误判为普通员工**。导入不报错，结果却是错的，这是最难发现的一类缺陷 |
| 改正 | 步骤 7 为绑定部门经理，步骤 8 为派生角色；步骤 8 开头写明前置依赖 |
| 理由 | 数据依赖决定执行顺序。在文档中显式写出依赖，而不是只靠步骤编号暗示 |
| 影响范围 | `03-database.md` §5 |

## #3 分级管理下的提权漏洞：缺少授权上界

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-20，纳入分级管理需求时 |
| 问题 | 分公司管理员持有 `sys:account:*` 权限、数据范围 `DEPT_AND_SUB`，可以给本分公司的用户分配角色、授予权限。原设计只校验「目标用户在不在我的范围内」 |
| 为什么错 | 分公司管理员可以给下属（或自己的小号）授予**全公司范围**的权限，再用那个账号越过自己的管理边界。管理范围被绕过了，而且每一步单独看都是合法操作 |
| 改正 | 增加授权上界规则 S-13：`可授予(a, p, s) = p ∈ EffectivePermissions(a) ∧ s ⊆ DataScope(a, p)`。管理员只能授予自己拥有、且范围不超过自己的权限 |
| 理由 | 规则放在**写路径**（配置接口），不进判定管道：它约束的是「能不能配」而非「能不能用」，配置操作的调用量只有鉴权的万分之一。没有另起一套 `admin_scope` 机制，因为分级管理本身就是数据范围作用于管理接口（见 `02-architecture.md` §4.1） |
| 影响范围 | SRS §3.2.2.1、S-13；`rbac-api.yaml` 两个授予接口的说明与错误码 |

## #4 多实例下 Redis 故障时继续使用本地缓存会破坏一致性

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，按质量属性逐项复查架构时 |
| 问题 | SRS §5.3 与 §6.2 写的是「Redis 不可用时降级为仅使用进程内缓存，功能不中断，不影响正确性」 |
| 为什么错 | 部署视图有两个以上实例，每个实例有自己的 Caffeine。实例之间的失效消息靠 Redis 传递。Redis 宕机后：管理员在实例 A 撤销许禄的权限，实例 B 收不到消息，许禄的请求落到实例 B 上**仍然放行**，直到 30 分钟 TTL 过期。原文「不影响正确性」只在单实例下成立 |
| 改正 | Redis 不可用时**绕过进程内缓存，直读数据库**；Redis 恢复后先清空进程内缓存再启用 |
| 理由 | 这是可用性与一致性的冲突（`02-architecture.md` T-3），按「安全性 > 可用性」取舍。代价可以承受：真实峰值约 400 QPS（SRS §5.0），数据库直读扛得住，损失的是性能而不是正确性。**→ 这条理由的依据已在 #7 修正**：10,000 QPS 是需求指标，降级期间暂停适用，不能说「扛得住」 |
| 影响范围 | SRS §5.3、§6.2；`02-architecture.md` §4.2.1 |

## #5 失效广播通道未指定，且未考虑消息丢失

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，与 #4 同时发现 |
| 问题 | §4.2 只写了「写操作提交后发布 `PermissionChangedEvent`」，没有说这个事件怎么到达其他实例 |
| 为什么错 | Spring 的应用内事件只在本进程内传播，其他实例根本收不到。即使改用 Redis Pub/Sub，它也不持久化：实例断线重连期间发布的消息会永久丢失，该实例的本地缓存就一直是旧的 |
| 改正 | 失效消息走 Redis Pub/Sub；同时维护全局权限版本号 `rbac:perm:version`，每次变更 INCR；各实例每 500 ms 比对一次，发现漏收即清空本实例进程内缓存 |
| 理由 | 不换用带持久化的消息队列（如 Kafka）：为一个失效通知引入新的中间件，部署与运维成本远大于收益。版本号轮询是一次 Redis GET，成本极低，且把最坏情况下的不一致窗口限制在 500 ms，满足 A-12 的 ≤ 1 秒 |
| 影响范围 | `02-architecture.md` §4.2.1；SRS §6.2 |

## #6 文档对「鉴权发生在哪里」表述不清

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-27，组内评审提出 |
| 问题 | 文档一处说业务系统每次操作都调用权限中心，另一处说有缓存，读者无法判断缓存在哪一侧，也看不出为什么不在登录时鉴权一次 |
| 为什么错 | 设计本身一致，但文档没写清楚，评审者得出「前后矛盾」的结论。检查时老师同样会这样问 |
| 改正 | 新增 `02-architecture.md` §4.6：区分认证（登录时一次）与授权（每次操作）；比较三种方案；明确写出「两级缓存全部在权限中心内部，业务系统不缓存」 |
| 理由 | 同一个问题组内能提出来，老师也会提出来。把答案写成独立章节，而不是散落在缓存章节里 |
| 影响范围 | `02-architecture.md` §4.6；SRS A-23；`11-defense.md` 高频追问 |

## #7 性能指标的依据写成了「自设余量」，降级论证依赖它

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，对照 9/29 需求清单时 |
| 问题 | SRS §5.0 把 10,000 QPS 写成「我方在推算峰值 400 QPS 之上自设的 25 倍余量」，§5.2 注明「单节点」；#4 的改正理由、`02-architecture.md` T-3、答辩稿都以「真实峰值 400 QPS，数据库扛得住」为论据 |
| 为什么错 | 需求清单明确给出 10,000 QPS 与 6–8 台服务器，它是需求指标而不是余量。若仍说「数据库直读扛得住」，就等于声称降级时也满足万级 QPS——这做不到。老师一问「降级时 10,000 QPS 还达标吗」，原论证就站不住 |
| 改正 | 10,000 QPS 改为需求指标、按集群计；单应用节点目标 3,500 QPS（4 个节点坏 1 个仍达标）。降级模式明确写为「**保证正确性，性能指标暂停适用**」；400 QPS 的推算改作降级时业务仍可运转的依据 |
| 理由 | 降级模式本来就不该承诺正常态的性能。把「正确性优先」与「性能暂停适用」同时写明，比含糊地说「扛得住」更经得起追问 |
| 影响范围 | SRS §5、§6.2；`02-architecture.md` §1.1、§6；`11-defense.md` |

## #8 先决条件的演示规则与继承冲突

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，对照需求清单的示例「MANAGER 必须拥有 EMPLOYEE」时 |
| 问题 | V3 的演示先决条件是「部门经理须先为员工」 |
| 为什么错 | 迭代二中部门经理继承普通员工。约束作用于有效角色（A-21）时，这条规则**恒成立**，形同虚设；若改按直接角色校验，首次导入的一百多名部门经理又**全部违规**（导入只派生一个角色）。两种查法都不对，问题出在规则本身。这与 #1（互斥角色与继承）是同一类问题，当时只修了互斥，没有推广到先决条件 |
| 改正 | 创建先决条件时校验：目标角色在继承图上不得已继承前置角色，否则返回 `24005 CONSTRAINT_INEFFECTIVE`。演示规则改为「审计员须先为普通员工」，两者无继承关系，业务含义是审计员必须是正式员工 |
| 理由 | 保持「约束一律作用于有效角色」这一条统一规则，不为先决条件开例外；把无效规则挡在配置阶段，与 #1 的处理方式一致 |
| 影响范围 | `V3__rbac2_constraints.sql`；SRS §4.2.8、附录 E；`05-ui.md` §4.4；`09-test-plan.md` §3.4 |

> #1 与 #8 的教训：**修一个问题时要问「同类问题还在哪里」**。#1 发现的是「约束与继承的交互」，当时只检查了互斥约束。

## #9 契约声明的管理权限在数据库里不存在

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-10-01，写权限拦截器、准备让 admin 登录调接口时 |
| 问题 | `rbac-api.yaml` 给每个接口声明了所需权限（`system:user:list`、`authz:check:invoke` 等 30 余个），但这些权限码**在任何地方都不会被写进 `sys_permission`**：迁移脚本没有，导入器只导入权限清单里的 1,795 条业务权限 |
| 为什么错 | 按原设计部署后，`SYS_ADMIN` 没有任何管理权限，除超级管理员外没人能调用管理接口——§4.7「所有接口受权限控制」落地后恰好把所有人都挡在外面。而且这些码也塞不进原表结构：`sys_permission` 要求 `resource_id`、`action_id` 非空，而平台权限不属于清单里的任何功能点，`list`、`manage`、`invoke` 也不在 5 个操作的词汇表里。问题的根源是契约和数据库分头设计，没有人检查「契约里的每个权限码，数据库里都有吗」 |
| 改正 | `sys_permission` 增加 `perm_type`（`BIZ` / `PLATFORM`），`resource_id`、`action_id` 改为可空；V1 末尾内置 27 条平台权限，并授予 `SYS_ADMIN`（24 条）、`SEC_ADMIN`（5 条）、`AUDITOR`（2 条） |
| 理由 | 不另建平台权限表：判定热路径只认一个字符串集合，两类权限放同一张表，判定内核一行不用改。职责划分延续 SSD 的思路：继承与约束归安全管理员，审计查询归审计员，系统管理员都不持有 |
| 影响范围 | `V1__rbac0_baseline.sql`；`03-database.md` §3.1 sys_permission、§5.3 |

## #10 初始口令哈希与文档不符

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-10-01，第一次运行单元测试时 |
| 问题 | V1 注释写 admin、root 的初始口令是 `Admin@123`，但哈希 `$2a$10$N9qo8uLOi…` 是网上常见的示例值，并不对应 `Admin@123`。`svc_hr_sync` 也用了同一个哈希，注释却说是「随机强口令」 |
| 为什么错 | 按文档部署后管理员无法登录；而三个账号共用一个哈希，意味着知道其中一个口令就能登录全部三个。哈希是不可读的字符串，代码评审看不出来 |
| 改正 | 用 BCrypt（cost 10）重新生成 `Admin@123` 的哈希；`svc_hr_sync` 改为一个随机串的哈希（口令未记录，部署时由运维重置）。新增测试 `seedPasswordHashMatchesDocumentedInitialPassword`，把「文档写的口令」与「脚本里的哈希」绑在一起 |
| 理由 | 这类「文档与数据不一致」只有可执行的检查才能发现。测试让它从此不会再次悄悄出错 |
| 影响范围 | `V1__rbac0_baseline.sql`；`AuthenticationFunctionsTest` |

> #9 与 #10 的共同点：**都是写代码时才暴露的设计缺陷**，文档评审了五轮都没发现。这正是 `00-charter.md` 坚持「先搭骨架、后填功能」的原因——骨架一跑，契约、数据库、文档三者的不一致立刻显形。

## 因需求变化而做的调整

以下不是设计错误，而是需求澄清后的调整，单独列出以便区分。

| # | 调整 | 触发 | 说明 |
|---|---|---|---|
| R-1 | 账号状态由两态（启用/禁用）改为三态（正常/冻结/禁用） | 9/20 需求澄清会议 | 冻结可恢复、保留全部授权；合并成两态会让「临时停权」和「离职」在审计日志里无法区分 |
| R-2 | 预置「单角色模式」约束但默认停用 | 会议纪要：「不存在多个角色，但可能后续拓展」 | 数据模型保持多对多，确认后只需 `UPDATE enabled=1` |
| R-3 | 测试系统由 2 个功能点扩为 2 个模块 8 个功能点 | 会议：「至少两个系统，每个 3–4 个功能」 | 见 SRS A-29 |
| R-4 | 10 月底目标改为可自动测试、可部署的后端；接入老师发布的测试 | 9/29 组内进度安排 | 可测试性与可部署性的战术见 `02-architecture.md` §1.1 |
| R-5 | 账号三态由「正常/冻结/禁用」改为「启用/停用/删除」；取消到期自动解冻 | 9/29 需求清单 | 冻结的语义由停用承担，原禁用并入删除。`status` 取值与 `status_reason` 列调整，接口删去冻结/解冻两个，改用状态接口 |
| R-6 | 新增超级管理员 `SUPER_ADMIN`，判定时越过权限引擎 | 9/29 需求清单 | 推翻原决策 A-3（不设旁路）。原决策的顾虑用三条规则保留：旁路在状态校验之后、每次审计、人数上限 3。`SYS_ADMIN` 保留为走正常判定的日常管理角色 |
| R-7 | 角色指派增加授权部门 `scope_dept_id` | 9/29 需求清单：属于一个部门，但可以有多个部门的权限 | 原设计的数据范围只能以本人部门为基准。`sys_user_role` 唯一键由 `(user_id, role_id)` 扩为 `(user_id, role_id, scope_dept_id)` |
| R-8 | 权限一律人工分配和回收 | 9/29 需求清单 | 三处自动行为改为人工：HR 同步不再派生角色；时间约束到期只失效不删除；取消自动解冻。岗位派生只在首次导入执行一次 |
| R-9 | 每一次鉴权都记日志，另建鉴权日志表 | 9/29 需求清单：记录 AUTH_SUCCESS | 原设计只记拒绝。取舍见 `02-architecture.md` T-6 |
| R-10 | DSD 由「可选」改为「必须」，时间约束由扩展功能转正 | 9/29 需求清单的 RBAC2 基线 | |
| R-11 | 部门表支持多棵树（多家公司） | 9/29 需求清单：多个公司、多权限域 | 表结构不变，只放开「单根」校验。是否需要强隔离待确认（SRS C.3 Q21） |
| R-12 | 所有接口声明所需权限，CI 检查无遗漏 | 9/29 教师强调 | 原契约有 6 个接口只要求登录，已补齐 |
| R-13 | 测试系统改为独立部署的外部模拟系统 | 9/29 需求清单：「外部模拟系统」 | 新增 `rbac-mock-biz` 模块，经 HTTP 调用权限中心 |
| R-14 | JDK 17 改为 21；部署环境确定为华为云 3 台 2 核 2G（1 编译 + 2 部署） | 9/30 组内 | 编排文件不变，按节点标签放置服务；性能只能推算（`02-architecture.md` §6.1） |

> 上述调整**均未改动任何表的主键**。唯一的结构性变化是 R-7：指派多了一个授权部门，唯一键随之多一列；其余全部是增列、增表或改取值。14 条调整中大部分只是「往管道里插一个阶段」或「往约束表里加一类规则」——这说明元模型的选择经受住了两轮需求变化，这一点本身可以作为答辩素材。
