# 设计问题与改正记录

> 第二次检查（11 月底）要求能回答「**设计问题和改正的理由**」。本文档记录设计过程中发现的每一个问题：发现了什么、为什么错、怎么改、为什么这样改。
>
> **规则**：凡是改了设计，就在这里追加一条，不删除旧条目。条目编号不复用。
>
> **阅读提示**：#36–#38 是 2026-10-14 按验收前调试清单改正的问题；#33–#35 是同日按外部调试报告改正的问题；#30–#32 是实现前端时发现的问题。#1–#14 写于范围收敛之前，其中涉及的角色继承、约束、两级缓存、`func`/`dao` 分层等设计，已在 #15–#29（2026-10-11 按第一次已知问题审查与 RBAC0 需求清单整改）中移除或改写。旧条目保留，作为「为什么改」的来历。

## #1 互斥角色演示对在引入继承后不可满足

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-20，设计 V3 约束脚本时 |
| 问题 | 静态互斥（SSD）的演示规则选的是「普通员工 ⟂ 部门经理」 |
| 为什么错 | 迭代二引入角色继承后，部门经理继承普通员工。约束作用于**有效角色**（A-21），所以每个部门经理都同时有效持有两个角色，**全部违反约束**——这条规则不可能被满足。迭代一不会暴露，到迭代二才会炸 |
| 改正 | 演示对改为「审计员 ⟂ 系统管理员」；并新增规则：创建 SSD 约束时校验规则内任意两角色在继承图上不得互为祖先，违反返回 `24005 CONSTRAINT_INEFFECTIVE` |
| 理由 | 只换演示数据治标不治本，管理员以后仍可能配出同样的无效规则。在写路径上校验，把错误挡在配置阶段。审计员与系统管理员的互斥也有真实的业务含义：审计员监督系统管理员，两者合一则审计失去独立性 |
| 影响范围 | `V3__rbac2_constraints.sql`、`rbac-api.yaml`（错误码 24005）、SRS CSTR-001 |

## #2 数据导入步骤顺序颠倒

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-20，复查导入设计时 |
| 问题 | 导入流程中「按岗位派生用户角色」排在「绑定部门经理」之前 |
| 为什么错 | 岗位→角色的配置规则中，优先级 2、3 通过 `sys_department.manager_user_id` 判断「此人是否为部门经理」。派生先执行时该字段还是空的，**所有部门经理与项目经理都会被误判为普通员工**。导入不报错，结果却是错的，这是最难发现的一类缺陷 |
| 改正 | 步骤 7 为绑定部门经理，步骤 8 为派生角色；步骤 8 开头写明前置依赖 |
| 理由 | 数据依赖决定执行顺序。在文档中显式写出依赖，而不是只靠步骤编号暗示 |
| 影响范围 | `03-database.md` §5 |

## #3 分级管理下的提权漏洞：缺少授权上界

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-20，纳入分级管理需求时 |
| 问题 | 分公司管理员持有 `sys:account:*` 权限、数据范围 `DEPT_AND_SUB`，可以给本分公司的用户分配角色、授予权限。原设计只校验「目标用户在不在我的范围内」 |
| 为什么错 | 分公司管理员可以给下属（或自己的小号）授予**全公司范围**的权限，再用那个账号越过自己的管理边界。管理范围被绕过了，而且每一步单独看都是合法操作 |
| 改正 | 增加授权上界规则 S-13：`可授予(a, p, s) = p ∈ EffectivePermissions(a) ∧ s ⊆ DataScope(a, p)`。管理员只能授予自己拥有、且范围不超过自己的权限 |
| 理由 | 规则放在**写路径**（配置接口），不进判定管道：它约束的是「能不能配」而非「能不能用」，配置操作的调用量只有鉴权的万分之一。没有另起一套 `admin_scope` 机制，因为分级管理本身就是数据范围作用于管理接口（见 `02-architecture.md` §4.1） |
| 影响范围 | SRS §3.2.2.1、S-13；`rbac-api.yaml` 两个授予接口的说明与错误码 |

## #4 多实例下 Redis 故障时继续使用本地缓存会破坏一致性

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，按质量属性逐项复查架构时 |
| 问题 | SRS §5.3 与 §6.2 写的是「Redis 不可用时降级为仅使用进程内缓存，功能不中断，不影响正确性」 |
| 为什么错 | 部署视图有两个以上实例，每个实例有自己的 Caffeine。实例之间的失效消息靠 Redis 传递。Redis 宕机后：管理员在实例 A 撤销某员工的权限，实例 B 收不到消息，该员工的请求落到实例 B 上**仍然放行**，直到 30 分钟 TTL 过期。原文「不影响正确性」只在单实例下成立 |
| 改正 | Redis 不可用时**绕过进程内缓存，直读数据库**；Redis 恢复后先清空进程内缓存再启用 |
| 理由 | 这是可用性与一致性的冲突（`02-architecture.md` T-3），按「安全性 > 可用性」取舍。代价可以承受：真实峰值约 400 QPS（SRS §5.0），数据库直读扛得住，损失的是性能而不是正确性。**→ 这条理由的依据已在 #7 修正**：10,000 QPS 是需求指标，降级期间暂停适用，不能说「扛得住」 |
| 影响范围 | SRS §5.3、§6.2；`02-architecture.md` §4.2.1 |

## #5 失效广播通道未指定，且未考虑消息丢失

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，与 #4 同时发现 |
| 问题 | §4.2 只写了「写操作提交后发布 `PermissionChangedEvent`」，没有说这个事件怎么到达其他实例 |
| 为什么错 | Spring 的应用内事件只在本进程内传播，其他实例根本收不到。即使改用 Redis Pub/Sub，它也不持久化：实例断线重连期间发布的消息会永久丢失，该实例的本地缓存就一直是旧的 |
| 改正 | 失效消息走 Redis Pub/Sub；同时维护全局权限版本号 `rbac:perm:version`，每次变更 INCR；各实例每 500 ms 比对一次，发现漏收即清空本实例进程内缓存 |
| 理由 | 不换用带持久化的消息队列（如 Kafka）：为一个失效通知引入新的中间件，部署与运维成本远大于收益。版本号轮询是一次 Redis GET，成本极低，且把最坏情况下的不一致窗口限制在 500 ms，满足 A-12 的 ≤ 1 秒 |
| 影响范围 | `02-architecture.md` §4.2.1；SRS §6.2 |

## #7 性能指标的依据写成了「自设余量」，降级论证依赖它

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，对照 9/29 需求清单时 |
| 问题 | SRS §5.0 把 10,000 QPS 写成「我方在推算峰值 400 QPS 之上自设的 25 倍余量」，§5.2 注明「单节点」；#4 的改正理由、`02-architecture.md` T-3、答辩稿都以「真实峰值 400 QPS，数据库扛得住」为论据 |
| 为什么错 | 需求清单明确给出 10,000 QPS 与 6–8 台服务器，它是需求指标而不是余量。若仍说「数据库直读扛得住」，就等于声称降级时也满足万级 QPS——这做不到。老师一问「降级时 10,000 QPS 还达标吗」，原论证就站不住 |
| 改正 | 10,000 QPS 改为需求指标、按集群计；单应用节点目标 3,500 QPS（4 个节点坏 1 个仍达标）。降级模式明确写为「**保证正确性，性能指标暂停适用**」；400 QPS 的推算改作降级时业务仍可运转的依据 |
| 理由 | 降级模式本来就不该承诺正常态的性能。把「正确性优先」与「性能暂停适用」同时写明，比含糊地说「扛得住」更经得起追问 |
| 影响范围 | SRS §5、§6.2；`02-architecture.md` §1.1、§6；`11-defense.md` |

## #8 先决条件的演示规则与继承冲突

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-09-29，对照需求清单的示例「MANAGER 必须拥有 EMPLOYEE」时 |
| 问题 | V3 的演示先决条件是「部门经理须先为员工」 |
| 为什么错 | 迭代二中部门经理继承普通员工。约束作用于有效角色（A-21）时，这条规则**恒成立**，形同虚设；若改按直接角色校验，首次导入的一百多名部门经理又**全部违规**（导入只派生一个角色）。两种查法都不对，问题出在规则本身。这与 #1（互斥角色与继承）是同一类问题，当时只修了互斥，没有推广到先决条件 |
| 改正 | 创建先决条件时校验：目标角色在继承图上不得已继承前置角色，否则返回 `24005 CONSTRAINT_INEFFECTIVE`。演示规则改为「审计员须先为普通员工」，两者无继承关系，业务含义是审计员必须是正式员工 |
| 理由 | 保持「约束一律作用于有效角色」这一条统一规则，不为先决条件开例外；把无效规则挡在配置阶段，与 #1 的处理方式一致 |
| 影响范围 | `V3__rbac2_constraints.sql`；SRS §4.2.8、附录 E；`05-ui.md` §4.4；`09-test-plan.md` §3.4 |

> #1 与 #8 的教训：**修一个问题时要问「同类问题还在哪里」**。#1 发现的是「约束与继承的交互」，当时只检查了互斥约束。

## #9 契约声明的管理权限在数据库里不存在

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-10-01，写权限拦截器、准备让 admin 登录调接口时 |
| 问题 | `rbac-api.yaml` 给每个接口声明了所需权限（`system:user:list`、`authz:check:invoke` 等 30 余个），但这些权限码**在任何地方都不会被写进 `sys_permission`**：迁移脚本没有，导入器只导入权限清单里的 1,795 条业务权限 |
| 为什么错 | 按原设计部署后，`SYS_ADMIN` 没有任何管理权限，除超级管理员外没人能调用管理接口——§4.7「所有接口受权限控制」落地后恰好把所有人都挡在外面。而且这些码也塞不进原表结构：`sys_permission` 要求 `resource_id`、`action_id` 非空，而平台权限不属于清单里的任何功能点，`list`、`manage`、`invoke` 也不在 5 个操作的词汇表里。问题的根源是契约和数据库分头设计，没有人检查「契约里的每个权限码，数据库里都有吗」 |
| 改正 | `sys_permission` 增加 `perm_type`（`BIZ` / `PLATFORM`），`resource_id`、`action_id` 改为可空；V1 末尾内置 27 条平台权限，并授予 `SYS_ADMIN`（24 条）、`SEC_ADMIN`（5 条）、`AUDITOR`（2 条） |
| 理由 | 不另建平台权限表：判定热路径只认一个字符串集合，两类权限放同一张表，判定内核一行不用改。职责划分延续 SSD 的思路：继承与约束归安全管理员，审计查询归审计员，系统管理员都不持有 |
| 影响范围 | `V1__rbac0_baseline.sql`；`03-database.md` §3.1 sys_permission、§5.3 |

## #11 数据流图违反画法规则

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-10-01，对照课件 3「结构化软件设计」复查 `06-detail-structured.md` 时 |
| 问题 | ① 2 级图在「查缓存」处画了「命中 / 未命中」两条分支；② 0 级图的外部实体是管理员、业务系统、普通用户，1 级图却只有管理员和业务系统，还多出一个 0 级图没有的 xlsx 数据源；③ 1 级图大部分数据流没有名字 |

| 改正 | 2 级图改为纯数据流：缓存作为数据存储，3.3–3.5 写入、3.6 读取，「何时跳过 3.3–3.5」移到结构图表达；0 级图改为上下文图，补 HR 系统与数据文件两个外部实体；1 级图补齐外部实体并给每条数据流命名，附平衡检查表；新增 3.0 的数据字典 |
| 理由 | DFD 是结构化设计的**输入**，变换分析要从 DFD 里找输入流、变换中心、输出流；DFD 里混进控制流，就找不出变换中心 |
| 影响范围 | `06-detail-structured.md` §2.1–§2.3、§2.5 |

## #13 判定函数接口偏宽、权限码格式知识分散

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-10-01，按课件 3 的深模块清单与「按决策设计」检查 `authorize` 时 |
| 问题 | ① `authorize` 有 7 个参数，其中 3 个是依赖，每个调用点都要自己备齐；迭代二加继承闭包还要再加一个；② 「权限码 = 资源 + 冒号 + 操作」这条知识在两处：判定函数负责拼、拦截器负责拆；③ `AuthenticationFunctions` 是通信内聚，授权判定为了一个 `subjectDenyReason` 依赖了整个登录模块 |
| 为什么是问题 | ① 接口宽会把复杂度推给调用者（课件：把复杂性留在模块内部），而且每次迭代都要改所有调用点；② 格式一变要改两处，漏一处编译器不报错；③ 口令规则与账号状态规则的变化原因不同，放在一起，改一个会波及另一个的使用者 |
| 决定 | **迭代一不改代码，迭代二一起改**：加入继承闭包依赖时，把依赖收拢为一个 `AuthzStores` 记录（参数 7 → 5）；把权限码的拆分移到 `PermissionSetFunctions`、与拼接放在一起；拆出 `SubjectFunctions` |
| 理由 | 现在只有两个调用点，改动收益小；迭代二本来就要改 `authorize` 的签名，一起改只动一次调用点。①的根源是结构化范式「依赖只能经参数传入」，这一点记入 `10-paradigm-comparison.md` 作为范式代价的证据 |

## #37 Redis 版本号递增失败时旧授权在 TTL 内继续生效

| 字段 | 内容 |
|---|---|
| 发现时间 | 2026-10-14，验收前调试清单 |
| 问题 | 授权缓存的版本号存在 Redis，授权修改提交**之后**再 `INCR`。`INCR` 失败只记错误日志：此时数据库已改、版本号没变，缓存在 TTL（10 分钟）内继续返回旧授权，回收的权限仍然可用 |
| 为什么错 | 需求是「权限修改后，在下一次访问时更新」。旧设计把这个窗口写成「唯一的不一致窗口，由运维告警兜底」，等于承认在 Redis 抖动时不满足需求；而且这是安全方向的错误（该拒的放行了） |
| 改正 | 版本号移到 MySQL（V2 新增 `sys_grant_version`，一行）。授权修改在**同一个事务**里 `version = version + 1`，与数据一起提交或回滚；更新到的行数不是 1 就抛异常，整个修改回滚。判定时先从 MySQL 读版本号、再按它读 Redis。读写事务里不写回缓存（可能含本事务未提交的修改）。Redis 只存数据，不参与失效 |
| 理由 | 调试清单给了三个方向：不用缓存、Redis 失败时绕过缓存、可证明的失效机制。不用缓存违背「提供数据库缓存设计」；「失败时绕过」只能让本副本知道，其他副本仍读旧键。同一事务提交是可证明的：读到新版本号的请求随后读到的一定是新数据，读到旧版本号的请求写回的是没人再读的旧键。代价是每次判定多一次按主键读一行；判定本来就要读 `sys_user`，缓存省下的一直是授权连表查询。版本行在修改事务提交前被锁住，并发的授权修改排队，读请求不受影响 |
| 影响范围 | `V2__grant_version.sql`、`GrantVersion`、`GrantVersionMapper`；`AuthorizationService.loadGrants`、`bumpGrantVersion`（原 `invalidateAfterCommit`）；`GrantCacheMapper` 去掉版本号；`AcceptanceTest.t12b_revocationDoesNotDependOnRedis`、`RedisFailureTest` |

## #39 被拒绝、失败的管理操作有一部分没有审计

| 字段 | 内容 |

| 发现时间 | 2026-10-15，组内检查「各种操作成功失败是否都被记录到日志里」 |

| R-16 | 管理员可以撤销自己的权限 | 10/15 课堂口头要求 | 原来回收自己的指派也要过管理范围检查：自己在管理范围外的部门持有的指派，自己撤不掉。现在回收自己的指派不查管理范围（单个、批量同一个 `checkRevoke`）。放弃权限不会扩大任何人的能力，所以不需要上界检查。唯一的例外是不能回收最后一个有效的超级管理员。撤掉自己的管理员角色后，下一次请求就失去管理能力，要恢复只能由其他管理员重新分配。测试 T14b |
| R-17 | 用户编号预留一段给内部用户 | 10/15 课堂口头要求 | 1–9999 是内部账号：`root` = 1，`SYSTEM` 类型账号（内部测试、业务系统接入用，组内讨论时老师也提示过）由服务层在段内取「最大编号 + 1」，用原生 SQL 显式写入，用完返回 409。员工与临时用户（手工新增、导入）由 V3 把自增起点设为 10000。没有加数据库约束：MySQL 的 CHECK 不能引用自增列。用户类型建成后不能修改，所以分段只需在新增时保证。测试 `internalAccountsUseTheReservedIdRange`，导入测试断言员工编号都 ≥ 10000 |
| R-19 | 审计暂不分级 | 10/15 组内检查「日志没分级」 | 不加「严重级别」列。RBAC0 需求对审计的要求是七要素与列出的事件类型，没有分级；`event_type` + `result` + `reason` 已能筛选，Dashboard「异常访问」就是按它们定义的一级。若组内或老师要求分级，做法是 V4 加 `level` 列（由事件类型与结果推出，如登录失败、越界、保护对象被拦为 WARN），审计查询与页面各加一个筛选条件 |
| R-21 | 取消账号到期时间 | 10/21 组内转述老师意见：不要「到期」功能，临时用户用完人工停用 | 课程要求的账号状态只有启用、停用、删除三种；`expires_at` 让「到期」成了事实上的第四种状态（`SUBJECT_EXPIRED`），还要求新增临时用户必须填到期时间。V4 删除该列，删列前把已到期、仍为启用的账号改为停用并写明原因；临时用户仍没有工号、电话（需求清单第 9 条）。接口去掉 `expiresAt` 字段与 `SUBJECT_EXPIRED` 原因码，前端去掉到期时间输入。测试 `t03_temporaryUserHasNoEmployeeInfoAndIsDisabledByHand` |
| R-20 | 允许跨公司授权 | 10/21 组内审查（C 环节问题清单，评为紧急） | 推翻原「适用部门必须与用户同公司」（`CROSS_COMPANY`，超级管理员也不行，要跨公司就另建账号）。用户只能属于一家公司，所以这条规则把每个人的授权锁死在所属公司里；另建账号又让同一个人有两个身份。现在删去这一条，其余照旧：公司内角色只能指派到本公司的部门；操作者对用户所属部门、适用部门都要有分配权限（只管一家公司的管理员授不了）；授权上界按适用部门检查。分配没有放宽「用户所属部门要在管理范围内」，否则只管 B 的管理员就能给 A 公司的人加权限。随之调整两处（复核时发现跨公司后两边可能是不同的管理员）：① 回收改为只看适用部门：适用部门所在公司能收回别人在自己部门的权限。没有采用「两边管得到其一」：那样分公司管理员能撤掉所属部门在本分公司、但适用于整个公司的上级管理员角色。用户所在公司要收回，可以停用账号。② 鉴权接口查别人仍只看被查用户所属部门。10/21 曾加入「调用者在目标部门持有 rbac:authz:invoke 也可查，此时只返回结论」，供业务系统账号代查别家公司的人；10/22 组内认为多余并撤回：本项目的业务系统转发用户本人的令牌查自己，用不到这条路径，而管理控制台的鉴权页面也调用这个接口，留着它只能靠脱敏防止探出别家公司的人。停用、删除账号仍只由用户所在公司的管理员做。角色详情「用户」页按适用部门过滤，A 公司管理员能看到持有 A 部门指派的 B 公司员工，并能回收。表结构不变。测试 `assignmentsMayCrossCompaniesWithinManagementScope`、`t19_…`；Debug 记录 DBG-5 |
| R-18 | 确认角色不带部门 | 10/15 组内讨论「角色设计要不要有部门」 | 保持现设计，不改表：部门挂在指派的适用部门上，角色只是权限集合。角色带部门会让同一组权限按部门复制成上百个角色。理由见 [03 §4.6](03-database.md) |

> 上述调整**均未改动任何表的主键**。唯一的结构性变化是 R-7：指派多了一个授权部门，唯一键随之多一列；其余全部是增列、增表或改取值。14 条调整中大部分只是「往管道里插一个阶段」或「往约束表里加一类规则」——这说明元模型的选择经受住了两轮需求变化，这一点本身可以作为答辩素材。
