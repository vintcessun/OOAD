**版本 0.1（骨架）· 2026 年 9 月 20 日**

> ⚠️ **本文档为骨架**，数据在三个迭代中**逐步填充**，最终在迭代三（12/22 检查）成文。
>
> 这是本项目区别于其他小组的核心产出。课程要求「分别用结构化和面向对象的方式实现」，多数小组会交出两份代码；**我们交出两份代码加一份对比实验报告**。

---

## 1. 为什么这份对比是可信的

对比实验要有意义，必须先保证三个实现**做的是同一件事**。本项目的三条保证：

| 保证 | 机制 |
|---|---|
| 同一套需求 | 三者都实现 `01-srs.md` 的同一批需求编号 |
| 同一份数据 | 共用一套 MySQL schema 与同一份导入数据（111 部门 / 10000 用户 / 1795 权限） |
| 同一份契约 | 共用 `rbac-contract` 的 OpenAPI 定义 |
| **行为等价可验证** | `rbac-test-suite` 的约 50 条契约测试对三个实现跑相同输入、断言相同输出，全绿才算等价 |
| 同一套压测 | 同一份 JMeter 脚本分别打到三个端口 |

> 如果没有这些保证，所谓「对比」就只是「我们写了三份不同的代码」，得不出任何结论。**先证明等价，再比较差异**——这是实验方法本身。

## 2. 范式判定标准

三种实现必须各自满足准入标准，否则实验无效（例如结构化实现里偷偷用了策略模式，对比结论就被污染了）。

| 范式 | 准入标准 | 定义于 |
|---|---|---|
| 结构化（面向功能） | 数据过程分离、无状态静态函数、禁用继承与多态、功能分解 | `06-detail-structured.md` §1.2 |
| 面向对象 | 充血模型、GRASP、显式设计模式、依赖倒置 | `02-architecture.md` §5.2 |
| 函数式 | 不可变、纯函数、I/O 推到边界、函数组合、`Either` 错误表达 | `02-architecture.md` §5.3 |

**编码前评审，不达标退回重写。** 这一条写进 `00-charter.md` 的风险登记册（R3）。

## 3. 对比维度与度量方法

| 维度 | 度量方式 | 客观性 |
|---|---|---|
| **可扩展性** | 新增一类约束需**修改几个已有文件**、新增几个文件 | ★★★ 完全客观 |
| **圈复杂度** | 核心判定函数的圈复杂度（SonarQube / PMD） | ★★★ |
| **代码量** | 实现同一批需求的有效代码行数 | ★★★ |
| **测试成本** | 达到 90% 覆盖率所需的测试代码行数；是否需要 Mock 框架 | ★★★ |
| **性能** | QPS / P95 / P99 / GC 次数（同一压测脚本） | ★★★ |
| **缺陷密度** | 开发期间各实现被契约测试捕获的缺陷数 | ★★☆ |
| **安全隐患** | 需要「开发者记得做」而编译器不检查的地方有几处 | ★★☆ |
| **可读性** | 组内交叉评审打分 + 实现与规格说明的对应程度 | ★☆☆ 主观 |

> **第一条是最重要的**。它把「可扩展性」这个通常只能空谈的概念变成一个**可以数出来的数字**。迭代三的验收实验就是：为三个实现各新增一类「时间窗口约束」，统计改动文件数。

## 4. 核心对比样本（三个）

选取三个既有代表性、又贯穿三个迭代的样本：

### 样本一：约束求值的可扩展性

| 范式 | 表达方式 | 新增一类约束需要 |
|---|---|---|
| 结构化 | 枚举 + `switch` 分派 | 新增检查函数 + **修改 switch** + **修改枚举** |
| 面向对象 | 策略模式 + 组合 | 新增实现类（Spring 自动注册则不改既有代码） |
| 函数式 | 谓词组合 + 归约 | 新增一个函数 + 加入列表 |

**预期结论**：结构化在这一维度上有**固有劣势**，且这不是实现质量问题，而是范式特征——没有多态就只能靠分支分派。

### 样本二：缓存失效的事务边界

| 范式 | 机制 | 风险 |
|---|---|---|
| 结构化 | 每个写接口**手动**在事务提交后调用失效 | ⚠️ 新增接口时容易漏掉，编译器不提醒，**漏掉即安全漏洞** |
| 面向对象 | 观察者模式 + `@TransactionalEventListener(AFTER_COMMIT)` | 声明式保证，不会漏 |
| 函数式 | 副作用推到边界，由边界层统一处理 | 同上 |

**度量**：统计「需要开发者记得做、而编译器不检查」的地方有几处。这是一个可以数出来的**安全指标**。

### 样本三：有效权限计算

| 范式 | 与规格说明的对应程度 |
|---|---|
| 结构化 | 循环 + 临时集合，需要读几行才能看出在算什么 |
| 面向对象 | 逻辑分散在 `User` / `Role` / `RoleGraph` 三个类中，需要跳转 |
| 函数式 | `flatMap` 链**逐行对应**数学定义 |

这一样本用于说明：**函数式在纯计算场景下的表达力优势**。

## 5. 结论框架（待数据填充）

预先写下结论的**形式**，避免最后为凑结论而选择性使用数据：

### 5.1 预期结论（待验证）

| 假设 | 预期 | 验证方式 |
|---|---|---|
| H1 | 三种范式的**运行时性能差异在同一数量级内**，不构成选型依据 | 压测 QPS / P99 |
| H2 | 结构化在**新增需求**时的改动面显著大于另两者 | 改动文件数统计 |
| H3 | 函数式在**纯计算**上表达力最强，但在有状态、有副作用的场景需要额外包装 | 代码量 + 可读性评分 |
| H4 | 面向对象在**中等规模、需求持续演进**的系统上综合最优 | 综合各维度 |
| H5 | 结构化的**测试成本最低**（纯函数、无需 Mock 框架） | 测试代码行数 |

> **H1 与 H5 是反直觉的**，如果实测支持，本身就是有价值的发现：H1 反驳了「面向对象因虚函数调用所以慢」的流行说法；H5 说明结构化并非一无是处，它在可测试性上反而有优势。
>
> **如果实测结果与预期相反，如实记录并分析原因。** 实验的价值在于得到真实结论，而不是印证预设。这一条要在答辩时主动说明。

### 5.2 结论不会是什么

答辩时要避免的三种无价值结论：

| ❌ 无价值的结论 | 为什么无价值 |
|---|---|
| 「面向对象最好」 | 没有条件限定的结论等于没有结论 |
| 「函数式代码更短」 | 代码短不等于好，且高度依赖具体问题 |
| 「结构化已经过时」 | 事实上结构化在本项目的测试成本上有优势；且操作系统内核、嵌入式系统至今大量使用 |

**有价值的结论形式**：「在**什么条件下**，**哪个维度上**，**哪种范式**有**多大的**优势」——四个要素缺一不可。

## 7. 本文档对应的答辩设计点

**DP-1 三范式并行架构**（贯穿三次检查，迭代三重点陈述）

| 项 | 内容 |
|---|---|
| **需求是什么** | 课程要求同一套需求分别用结构化、面向对象实现，部分功能用函数式，并能说明各自的适用性 |
| **存在什么问题** | ① 三份实现若不隔离，范式边界会被侵蚀（结构化里混入多态），对比失效；② 若完全独立开发，无法证明它们做的是同一件事，对比不可信；③ 「哪种范式更好」若没有可度量的指标，只能流于空谈 |
| **采用什么方法与理由** | ① Maven 多模块 + 各实现模块互不依赖，编译期强制隔离；② 共用契约、schema、测试集，**行为等价成为可验证的事实**；③ 预先定义 8 个度量维度，其中「新增一类约束需修改几个已有文件」是完全客观的硬指标；④ 预先写下假设 H1–H5，实测与预期不符时如实记录 |
| **实现效果** | 待三个迭代完成后填充 |

> 答辩时的关键一句：**这不是「我们写了三遍」，而是一次有对照组的实验。** 等价性由契约测试保证，差异由 8 个维度度量，结论有条件限定。
