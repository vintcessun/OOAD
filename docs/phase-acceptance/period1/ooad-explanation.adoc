== 项目需求

本项目为多公司、多部门的业务系统建设统一权限中心。用户需要登录系统并访问已获授权的功能，管理员需要维护人员、角色和权限，业务系统需要得到可靠的访问判断，审计人员需要查明操作结果及原因。

其中最主要的业务要求是：*一个人归属一个部门，但可以在多个部门工作；他在各部门拥有的能力可以不同。* 例如，一名员工属于道路分公司，在道路分公司负责公文审批，同时在桥梁分公司只有公文查看权限。系统必须允许这两项工作，又不能因此允许他审批桥梁分公司的公文。

其他需求围绕这一授权模型展开：

[cols="2,4",options="header"]
|===
|需求 |本项目中的具体含义
|账号管理 |提供员工、临时用户和内部账号；支持启用、停用、逻辑删除。临时用户无工号和电话，使用结束后人工停用。
|授权管理 |权限授予角色，角色按适用部门分配给用户；支持单个、按部门、按公司批量操作。
|管理边界 |管理员只能管理范围内的人员和指派，不能把自己没有的权限授给别人，也不能把本人权限扩大为全部记录权限。
|及时生效 |角色停用、角色权限变化、指派回收提交后，新请求使用更新后的授权，即使请求落到另一个应用副本。
|解释与审计 |权限检查和解释使用同一判定过程；授权、回收、拒绝等行为留下主体、对象、时间、结果和原因。
|界面与接入 |菜单和按钮按权限展示，后端独立检查接口权限；外部业务系统负责执行“仅本人记录”等数据过滤。
|架构与验证 |当前阶段采用 Controller、Service、Mapper 三层结构，通过业务测试、架构测试和 JaCoCo 报告检查实现。
|===

== 主要设计问题及解决办法

=== 组织归属与工作权限如何分别表达

若把用户所属部门直接作为全部权限范围，跨部门工作无法表达；若把所有角色权限与所有部门范围分别合并，又会产生不存在的授权组合。

因此，用户表的 `department_id` 保存组织归属，指派表 `sys_user_role` 用“用户、角色、适用部门”保存一次授权。Role 保存可复用的权限集合，UserRole 保存它在哪个部门生效。公司内角色另外保存 company_id，限制其适用公司的范围。

鉴权查询把权限码、指派 ID、适用路径和 selfOnly 一起返回为 GrantRow。AuthorizationService 先从这些记录中筛出目标权限，再检查同一批记录的部门路径。上述道路审批、桥梁查看的例子中，桥梁审批会因路径不覆盖被拒绝。测试 `t07b_scopeBelongsToTheAssignmentNotToTheUnionOfRoles` 专门检查这一情况。

这种设计允许同一角色在不同部门复用，避免为每个部门复制一套角色。代价是权限计算必须保留指派来源，不能只传一个去重后的权限码集合。

=== 管理员怎样授权才不会扩权

拥有“分配角色”权限，只能说明管理员可以发起分配操作。给谁分配、在哪个部门生效、角色包含什么权限，还需要进一步检查。

AssignmentService 的 `checkOne` 先检查用户、角色和适用部门，再检查公司内角色是否属于适用部门所在公司。普通管理员还须同时管理用户所属部门和适用部门。随后 `escalation` 逐项比较拟授权限：操作者没有该权限，或只有本人权限而待授角色不限本人时，拒绝授出。

回收采用不同的范围规则。桥梁分公司需要能收回道路员工在桥梁的权限，因此 `checkRevoke` 只检查指派适用部门，不要求同时管理该员工的所属公司。分配和回收分别保留校验过程，能够表达这一业务差异。

给角色增加权限的影响更大，会改变所有持有者的能力。RoleManagementService 在公司根部门检查操作者的管理能力和拟授权限，而非仅检查某个下级部门。两类授权入口都需要防止扩权，但检查的范围层级不同。

=== 回收权限后怎样避开变更前的缓存

只等待缓存 TTL 到期，会延长已回收权限的可用时间；提交后删除 Redis 键，又可能因删除失败而留下旧数据。

项目把授权版本放在 MySQL 的 `sys_grant_version`。指派或角色权限变更与版本递增在同一事务提交，缓存键包含版本。例如回收前读取 v7，提交后版本为 v8；新请求只查 v8 键，变更前的 v7 键即使仍在 Redis 中也不会被命中。角色变更影响多名用户时，无需先计算逐人的失效名单。

这一方案依赖数据库现有事务，处理过程较短。其成本也明确：每次授权读取要查版本，一次修改会使所有用户的变更前版本的缓存失去复用机会，授权写操作竞争同一版本行。当前先满足多副本及时生效的要求；若压测发现版本行锁等待或回源量成为瓶颈，再考虑按用户、角色细分版本。

=== 批量和导入怎样处理部分错误

批量分配使用与单个分配相同的授出规则，但要提前汇总结果。一批包含两名合法下属、一名范围外人员和一个无效 ID 时，ATOMIC 整批不写入；PARTIAL 写入两名下属并报告两项失败。批量上下文复用角色权限和按部门计算的上界结果，再按 1000 个用户分段写入，减少重复查询。

权限导入还要区分明确撤权和无法判断。“无”表示撤去该项授权；空白或未知词表示数据异常，需要保留该资源的原有授权；所属系统或模块都无法定位时，本次暂停原有授权回收。ImportService 用 wanted、untouched 和 unresolvedRows 保存这些不同的处理状态。这样，不完整的表格不会被直接解释为管理员要求清空权限。

组织导入则先建部门、再导入员工、最后关联负责人。员工按“分公司＋部门”定位，避免道路财务部与桥梁财务部混淆。负责人候选来自本次创建的人员，负责人信息本身不产生授权。

=== 失败操作怎样留下记录

撤销最后一个有效超级管理员时，业务必须回滚，但拒绝尝试仍需要保留。因此 AuditService 使用独立事务：主事务中的删除回滚，审计中的 `ROLE_REVOKE / DENIED / LAST_SUPER_ADMIN` 留下记录。

独立审计的代价是成功日志可能先于业务最终提交。若主事务在提交阶段失败，已提交日志不会自动撤回。当前设计满足失败尝试留痕的要求，但没有实现成功审计与业务提交的原子一致性。

== 采用的分析与设计方法

=== 从业务概念到数据模型

分析阶段以员工、管理员、审计人员、业务系统为参与者，识别登录、鉴权、分配、回收、导入等用例，再提取 User、Department、Role、Permission、UserRole 等概念。

UserRole 是本项目较关键的分析结果：用户与角色之间除了关联，还需要适用部门、授权人、时间和理由。因此将“指派”作为单独记录，并为“用户＋角色＋适用部门”建立唯一键。数据库 ER 图、字段定义和三元指派都由这个业务含义推导而来。

=== 按功能组织当前实现

当前实现采用结构化设计。功能分为认证、鉴权、用户管理、指派、角色管理、目录、导入、菜单和审计统计；每项功能继续分解为输入校验、处理、数据访问和输出。

Controller 将 HTTP 请求转换为业务参数；Service 完成一次业务操作及其事务；Mapper 负责查询和写入。实体只保存记录，业务判断集中在 Service。Java 类和 Spring 依赖注入用于组织这些过程。

以角色分配为例，处理顺序为“读取用户与角色 → 校验管理范围和权限上界 → 写指派 → 更新版本 → 记录审计”。把这一过程放进 AssignmentService，能够让单个、批量入口共用规则，也方便确定事务范围。若由 Controller 直接写关联表，就会绕过这些检查。

=== 用共享过程保持判断一致

接口拦截、权限检查和解释共同使用 AuthorizationService 的判定过程。AuthzQueryService 另外负责“调用者能否查询这个人”，防止普通用户填写他人 userId 探测权限。

部门范围采用 `/祖先id/.../本id/` 路径，通过前缀比较判断覆盖。末尾分隔符避免 ID 1 与 10 混淆。此方法满足当前以子树为范围的查询；path 是冗余数据，后续若开放部门搬迁，必须一并更新后代路径和授权缓存。

=== 账号状态与使用管理

账号使用 ACTIVE（启用）、DISABLED（停用）、DELETED（删除）三种状态。管理员通过状态切换控制账号使用，临时用户完成工作后由管理员停用。删除操作保留用户记录并填写删除时间。

认证与鉴权在每次请求中检查账号状态。JWT 有效期控制令牌使用时间，连续登录失败达到阈值后通过 locked_until 限制登录。账号字段和状态约束见 xref:database-design.adoc[database-design.adoc（数据库设计说明书）]。

== 内聚、耦合与模块粒度

=== 授权判定：集中维护同一条授权依据

`decide` 的状态检查、授权读取、权限筛选、范围筛选和本人限制计算共同产生一个 Decision，具有较强的功能内聚。步骤之间也有顺序依赖：必须先得到覆盖目标的候选记录，再计算 selfOnly。否则，一个不覆盖目标部门的完整权限可能错误地取消本人限制。

整个 AuthorizationService 的职责比 decide 更宽，还负责缓存读取、范围计算、版本递增和拒绝审计。Assignment、AuthzQuery、Import、Menu、Org、RoleManagement、UserManagement 七个服务直接依赖它，分别使用其中不同的能力。

保留这一粒度的收益是授权数据的读取规则集中，菜单、列表和管理操作使用同一套有效角色数据。成本是授权记录结构变化会影响多个调用方。当前规则和存储围绕同一 RBAC0 模型演化；若未来判定规则、缓存和版本机制分别频繁变更，再拆出独立职责更有实际意义。

=== 指派管理：共用授出规则，分别处理回收

AssignmentService 的单个与批量分配共用 `context → checkOne → escalation`。这些方法围绕“建立合法指派”这一结果组织，具有功能内聚；共享角色权限、操作者授权和部门数据，也具有通信内聚的特点。

批量 Context 只活在本次调用中。同一适用部门的多名员工可以复用上界检查结果，又不会把一个请求的操作者数据留给下一次请求。相比单独复制一套批量服务，当前划分减少了两份安全规则不一致的风险。

回收保留 `checkRevoke`，因为回收不要求操作者拥有被撤回的业务权限，且范围检查只针对适用部门。这一差异决定了共用校验的限度。

复用也留下了接口成本：BatchAssign 的空 scopeDepartmentId 在分配和回收中含义不同；duplicated 在分配中表示已有指派，在回收中表示原本没有指派。接口文档和结果展示必须分别解释，不能只依赖字段名称。

=== 认证与令牌：按变化原因划分

AuthenticationService 维护账号状态、失败次数、注销和令牌版本；TokenService 负责 JWT 签发与解析。两者各自围绕身份检查和令牌协议组织，职责较集中。

调整“失败 5 次锁定 15 分钟”主要涉及认证服务与 UserMapper 的原子更新；替换 JWT 签发、解析实现主要涉及 TokenService 和配置。分开这两类变化，可以让令牌模块不需要理解部门、角色和登录计数。保留的耦合是解析结果中的 userId、version、jti、expiresAt 等字段，协议替换时仍要维持这一接口。

=== 导入：流程内部紧密，类的职责偏宽

组织导入的部门、人员、负责人处理有先后依赖；权限导入的单元格解析、授权更新和原有授权回收也需要连续执行。两条流程各自有顺序内聚。

但它们依赖的数据和变更原因不同：组织导入主要使用 Company、Department、User，权限导入主要使用 System、Module、Resource、Action、Permission、Role、RolePermission。ImportService 共依赖 10 个 Mapper、3 个 Service 和 Clock，类整体以内含两类 Excel 导入功能为边界，内聚弱于各自子流程。

当前只有两个固定上传入口，把流程保存在一处便于沿输入格式核对处理。保留成本是修改人员字段时也要阅读较大的导入类；员工导入只借用 UserManagementService 的初始口令哈希，自行创建用户，新增必填规则要同时检查人工创建和导入两条路径。若两类表格继续独立扩展，优先拆分组织导入与权限同步，比按每个解析步骤拆类更合适。

=== 审计与统计：共享数据，分开写入和计算

AuditService 围绕事件记录和查询，DashboardService 围绕指标计算。统计直接读取日志表，不调用审计写入，避免查询自身继续产生统计事件。两者按处理目的分开，便于单独修改指标算法。

仍需共同维护事件名、原因码、权限码格式和耗时单位。比如异常访问由“登录失败或无效主体鉴权”组成，AuditLogMapper 的 search 与 countAbnormal 各有一份条件。改动定义时须同步两处，否则 Dashboard 数字与点开后的日志列表不一致。现有 `abnormalAuditFilterMatchesDashboardCount` 检查这项一致性。

=== 主要耦合及维护成本

[cols="2,2,3",options="header"]
|===
|交互 |耦合类型与表现 |保留理由与修改影响
|covers(scopePath, targetPath) |数据耦合，输入两个路径、输出布尔值 |参数足以完成覆盖判断；路径格式由组织导入、范围判断和子树查询共同遵守。

|GrantRow / GrantSet |共享数据结构；连接 JPQL 构造投影、Redis 序列化和多个服务 |保留权限、范围与指派的对应关系；新增维度时需同步投影参数、缓存兼容性及消费方。
|explain、batch mode |控制耦合，参数决定轨迹输出或批次处理方式 |共用判定和校验；需分别测试两个分支。查询层 explain 还决定代查权限。
|写授权后推进版本 |执行顺序和事务依赖 |让数据与版本共同提交；新增写入口漏调不会被编译器发现，必须有回收生效测试。
|审计事件与统计查询 |共享事件分类和字段语义 |同一份数据支持追溯与统计；修改字符串、权限码分段或耗时单位会影响查询结果。
|http.ts 与 AuthHooks |回调接口及模块级共享配置 |避免 HTTP 层直接依赖 store/router；仍依赖启动装配顺序和错误码约定。
|===

多个服务调用同一个服务属于调用依赖。数据库和 Redis 是共享运行状态；前端 hooks 是模块级共享配置；批量 Context 则是调用内局部数据，生命周期不同。

=== 为什么采用目前的粒度

本项目先把安全规则集中在完整业务操作中，再用三层结构分离 HTTP、业务和持久化。这样，新增一种批量目标来源主要修改 resolveTargets，后续校验继续复用；新增页面主要增加组件映射、菜单与权限数据；修改登录阈值不需要改动角色管理。这些变化可以在有限范围内完成。

有些依赖需要保留。授权记录中的权限与范围不能拆开计算，授权写入与版本不能分开提交，审计与统计必须共享事件定义。单纯减少参数或增加服务层数，无法消除这些业务联系。

当前最明显的改进位置是导入职责过宽、人工创建与导入校验分散、版本推进依赖调用约定，以及审计字符串与统计条件的同步维护。它们是具体的维护成本。现阶段采用现有粒度，是为了让有限的业务流程和事务可以直接核对；后续拆分应针对这些成本及实际变化频率进行。
