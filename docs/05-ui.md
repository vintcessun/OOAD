# 前端界面设计说明书

**版本 1.0 · 2026 年 10 月 11 日** · 范围：RBAC0（第一次检查） · 技术栈：Vue 3 + TypeScript + Element Plus + Pinia + ECharts

> **当前状态（2026-10-12）**
> - 本文 15 个页面已全部在 [`rbac-web/`](../rbac-web/) 中实现（Vue 3 + TypeScript + Element Plus + Pinia + ECharts），对接 44 个后端接口（`/authz/check` 由业务系统调用，不在控制台出现）。
> - 测试：Vitest 单元测试覆盖请求与错误处理、登录与权限状态、路由守卫、`v-perm`、批量结果、Dashboard、权限解释；Playwright 端到端测试连真实后端、MySQL、Redis，在浏览器里走完「首次登录改口令 → 导入 → 批量授权 → 用户详情 → 回收 → 权限解释 → 角色授权 → 审计 → 普通员工 403」（`docs/09-test-plan.md` §1.1）。
> - 运行：后端在 8081 时 `cd rbac-web && npm ci && npm run dev`；部署时由 `rbac-web` 镜像（Nginx）提供页面。
> - 10/15：可运行的控制台作为界面原型交付，本文 §6 补写设计基线、页面状态与交互规则；个人中心可以撤销自己的指派（§3.12）。
>
> **与线框图的差异**（实现时的取舍）
> - 菜单目录默认全部展开；部门树默认只展开第一层（分公司一级），上百个部门全展开不便浏览。
> - Dashboard「异常访问数量」点击后跳到审计日志，从今天 0 点起、勾选「只看异常访问」（`abnormal=1`）。审计接口的 `abnormal` 条件与指标用同一个口径（登录失败 + 无效主体发起的鉴权），点进去看到的条数就是卡片上的数字；「缺少权限」「超出数据范围」这类正常的拒绝不在其中。
> - 热力图点击格子跳到同一时间段的 `AUTH_SUCCESS` 审计记录（审计接口没有按业务系统过滤的参数）。
> - 批量结果的失败清单用普通表格而不是 Element 表格，以便在弹窗中完整显示。

## 1. 设计目标

| # | 目标 | 说明 |
|---|---|---|
| 1 | **让权限可见** | 界面要回答的不只是「有哪些用户」，更是「谁通过哪个角色、在哪个部门范围内获得了什么权限」。用户详情页的每一条有效权限，都标明来源角色与适用部门 |
| 2 | **页面只做 RBAC0 需要的事** | 只有需求清单中的页面：Dashboard、用户、角色、权限、菜单、审计日志、组织与批量授权，以及「权限解释」「权限使用热力图」两项创新功能。不提供角色继承、约束、会话角色等 RBAC1/2 页面 |
| 3 | **前端控制只为体验** | 菜单隐藏、按钮禁用都不是安全边界。后端每个接口都由拦截器按契约中的 `x-required-permission` 独立鉴权，被操作的对象还要在 Service 里再校验一次管理范围 |
| 4 | **数字全部真实** | Dashboard 与热力图的每个数字都由后端从审计事件统计得出（§3.1），前端不放演示用的假数据 |
| 5 | **管理范围看得见** | 管理员只能管理适用部门及其下级。部门树、用户列表、角色列表只显示管理范围内的内容；越界操作即使从接口直接发起也会返回 403 |

### 2.2 动态生成规则

菜单由 `GET /menus/me` 返回，后端已经过滤：

- 叶子菜单挂一个 MENU 类型的资源（「前端菜单也是一种 Resource」）。用户持有「该资源:view」才下发。
- 目录节点（如「系统管理」）至少有一个子菜单可见时才下发。

前端拿到什么就渲染什么，不在本地另存一份菜单配置。各类账号看到的菜单：

| 账号 | 看到的菜单 |
|---|---|
| 超级管理员 | 全部（越过权限引擎） |
| 权限管理员（RBAC_ADMIN） | 全部 |
| 审计员（AUDITOR） | Dashboard、系统管理 › 审计日志、权限使用热力图 |
| 普通员工（没有任何 rbac:* 权限） | 菜单为空，只有右上角「个人中心」（本人详情、修改口令） |

> **隐藏菜单不等于后端放行。** 直接在地址栏输入 `/audit-logs`，或用工具构造 `GET /api/v1/audit-logs`，后端拦截器照样返回 403（验收用例 T18）。

## 3. 页面设计

每个页面按同一格式描述：对应需求 → 接口与权限 → 线框 → 字段与操作 → 异常状态。所有页面共用的错误处理见 §4.3。

### 3.0 登录与修改口令

| 项 | 内容 |
|---|---|
| 对应需求 | 「登录」场景；账号启用 / 停用 / 删除三态 |
| 接口 | `POST /auth/login`（免登录）、`POST /auth/password`、`GET /auth/me`、`POST /auth/logout`（均为 `@self`） |

```
┌────────────── 统一授权中心 ──────────────┐      ┌──────────── 首次登录，请修改口令 ────────────┐
│  用户名  [                    ]         │      │  旧口令    [                ]               │
│  口令    [                    ]         │      │  新口令    [                ]               │
│                                         │      │  确认新口令 [                ]               │
│  ⚠ 用户名或口令错误                       │      │  至少 8 位，含大写、小写、数字与特殊字符       │
│                     [ 登录 ]            │      │                          [ 确认修改 ]        │
└─────────────────────────────────────────┘      └─────────────────────────────────────────────┘
```

| 情形 | 后端返回 | 界面 |
|---|---|---|
| 用户名或口令错误、用户不存在、已删除 | 401 / 40102 | 统一显示「用户名或口令错误」，不区分是哪一种 |
| 连续失败 5 次 | 401 / 40103 | 「账号已锁定 15 分钟」 |
| 账号停用 | 401 / 40104 | 「账号已停用，请联系管理员」 |
| 登录成功但 `mustChangePwd = true` | 200 | 直接进入改口令页。此时除 `/auth/me`、`/auth/password`、`/auth/logout` 外，任何接口都返回 403 / 40304，前端统一跳回本页 |
| 改口令成功 | 200 | 旧令牌全部作废，前端清除令牌并回到登录页 |
| 登出 | 200 | 令牌在服务端登记为已注销，再用会得到 401 |

#### 3.1.1 Dashboard 十一项指标的统计口径

所有数字都由后端 `DashboardService` 实时统计。数据来源只有用户、角色、权限三张表，以及审计日志 `sys_audit_log` 中的真实事件，不做演示用的假数据。

「鉴权事件」指 `event_type` 为 `AUTH_SUCCESS` 或 `AUTH_FAILED` 的审计记录，包括两种来源：

- 业务系统（或用户本人）调用 `/authz/check`、`/authz/explain` 发起的判定；
- 管理接口经权限拦截器做的判定。

| # | 指标 | 口径 |
|---|---|---|
| 1 | 用户数量 | 未删除的用户（`status <> 'DELETED'`），包含已停用用户与临时用户 |
| 2 | 角色数量 | 全部角色（含停用、内置、全局与公司内角色） |
| 3 | 权限数量 | `sys_permission` 的行数，即已定义的「资源 × 操作」组合 |
| 4 | 今日鉴权次数 | 今天 0 点起的鉴权事件数 |
| 5 | 鉴权成功率 | 今日 `AUTH_SUCCESS` 数 ÷ 今日鉴权次数；分母为 0 时显示 0 |
| 6 | 鉴权失败率 | 今日 `AUTH_FAILED` 数 ÷ 今日鉴权次数。失败指判定结论为拒绝，不是调用出错 |
| 7 | P95 延迟 | 今日鉴权事件 `latency_us` 的第 95 百分位，用最近秩法（排序后取第 ⌈0.95·n⌉ 个），换算为毫秒 |
| 8 | P99 延迟 | 同上，取第 99 百分位 |
| 9 | QPS | 最近 60 秒的鉴权事件数 ÷ 60 |
| 10 | 缓存命中率 | 今日鉴权事件中，授权数据来自 Redis 缓存（`cache_hit = true`）的比例 |
| 11 | 异常访问数量 | 今日登录失败的次数，加上由已停用、已删除或不存在的主体发起的鉴权次数（拒绝原因为 `SUBJECT_DISABLED` / `SUBJECT_DELETED` / `SUBJECT_NOT_FOUND`）。这类请求说明有人在用不该再有效的身份访问系统 |

> 本阶段没有性能验收目标，Dashboard 只如实展示测量值，不为了让数字「好看」做专门的性能优化。

**字段与操作**

| 操作 | 说明 |
|---|---|
| 列表 | 只列出管理范围内的用户（后端按操作者的适用部门过滤）。默认不含已删除用户，状态下拉选「已删除」时才显示 |
| 新增 | 弹窗字段：用户名、姓名、部门（部门树，只能选管理范围内的）、类型、工号、电话、岗位、初始口令。<br>· 类型为「临时用户」时：隐藏工号与电话；没有到期时间，用完由管理员停用。<br>· 类型为「正式员工」时：工号必填。<br>· 口令留空则使用初始口令，并要求首次登录修改 |
| 编辑 | 可改姓名、部门、电话、岗位。调入的部门也必须在管理范围内，且不能跨公司 |
| 停用 / 启用 | 二次确认并填写原因。停用后该用户手中的令牌在下一次请求即失效 |
| 删除 | 逻辑删除，二次确认。删除后用户名不能复用，已有指派保留供审计 |
| 批量启用 / 停用 / 删除 | 勾选后提交 `POST /users/batch-status`。后端逐个校验、逐个执行，返回成功数与失败清单（原因如 `OUT_OF_MANAGE_SCOPE`、`CANNOT_CHANGE_SELF`、`TARGET_IS_SUPER_ADMIN`） |

不能停用或删除自己；持有超级管理员角色的账号，只有超级管理员能改。

**批量授权弹窗**（`POST /assignments/batch`；批量回收结构相同，调 `/assignments/batch-revoke`）

```
┌──────────────────────── 批量授权 ────────────────────────┐
│  目标      ○ 分公司   ● 部门   ○ 员工（使用列表中勾选的人） │
│            [道路工程分公司 ▾]  ☑ 含下级部门                │
│  角色      [部门经理 ▾]                                   │
│  适用部门  ● 各自所属部门   ○ 指定部门 [          ▾]       │
│  原因      [新项目部成立                ]                 │
│  执行方式  ● 整批原子（有一人不通过就全部不执行）           │
│            ○ 部分执行（执行通过的，列出失败的）             │
│                                          [取消] [提交]    │
├──────────────────────── 提交结果 ────────────────────────┤
│  ✗ 未执行：3 人未通过校验（整批原子模式）                    │
│    用户 1043  OUT_OF_MANAGE_SCOPE   不在你的管理范围内      │
│    用户 2210  PRIVILEGE_ESCALATION  该角色含你没有的权限    │
│    用户 9999  NOT_FOUND             用户不存在              │
│  请求 120 人 · 成功 0 · 已持有 4 · 失败 3                    │
│                         [改为部分执行再提交] [关闭]          │
└──────────────────────────────────────────────────────────┘
```

| 字段 | 对应请求参数 | 说明 |
|---|---|---|
| 目标 | `targetType` = COMPANY / DEPARTMENT / USER，`targetIds` | 分公司与部门从组织树选，员工取列表勾选 |
| 含下级部门 | `includeDescendants` | 只对部门目标有效，默认勾选 |
| 适用部门 | `scopeDepartmentId` | 留空 = 每个人各自的所属部门 |
| 执行方式 | `mode` | 默认 ATOMIC；PARTIAL 需要用户主动切换 |

提交结果展示 `BatchResult` 的全部字段：`committed`、`requested`、`succeeded`、`duplicated`、`failed`、`failures[]`。

- 「已持有」（`duplicated`）不算失败，只用于提示。
- 整批原子模式下 `committed = false`，界面明确告诉用户**这一批一个都没写入**，并提供「改为部分执行再提交」按钮。避免管理员误以为全体都已授权。

**分配角色弹窗**

- 字段：角色（只列启用的角色）、适用部门（默认所属部门，只能选管理范围内的部门）、原因。
- 后端拒绝时按错误码提示：

| 错误码 | 提示 |
|---|---|
| 40302 | 用户或适用部门不在你的管理范围内 |
| 40303 | 该角色含有你在适用部门不具备的权限，不能授出 |
| 409 | 该用户在该部门已持有此角色 |
| 400 | 公司内角色只能指派到本公司的部门 |

- 适用部门可以选别的公司（跨公司授权，`12-design-log.md` R-20）；部门选择器换公司时清空已选部门。用户详情的角色表里，适用部门不在该用户所属公司的指派带「其他公司」标记，因为两家公司都有「财务部」，只看部门名分不清。「指定部门」未选部门时「分配」按钮不可用，避免后端落到用户所属部门。

**回收**

- 二次确认，回收后该用户下一次请求即失去这一指派带来的权限。
- 不能回收最后一个有效的超级管理员（409）。
- 回收某人的管理员角色，不影响他过去授给别人的指派。

**有效权限页签**

```
│  有效权限（94 条）    🔍[权限码/资源]  [业务系统 ▾]  ☐只看「只限本人」           │
│  ┌───────────────────────┬──────────┬─────────────────────┬────────┐         │
```

- 每条有效权限都带着它来自哪次指派（来源角色 + 适用部门）。同一个权限码可能出现多行（不同角色或不同部门），不合并，否则看不出作用域。
- 「只限本人」来自权限清单中的「查看本人」「编辑本人」，由业务系统按记录归属过滤。

- 超级管理员的详情页顶部显示「超级管理员：越过权限引擎」，有效权限页签显示说明文字，不列条目。
- 数百条权限必须能按业务系统筛选、按权限码搜索。系统管理员模板有 1,795 条，不能筛选的列表没人能用。

|---|---|
| `SUBJECT_NOT_FOUND` / `SUBJECT_DISABLED` / `SUBJECT_DELETED` | 用户不存在 / 已停用 / 已删除 |
| `MISSING_PERMISSION` | 当前角色均不包含该权限（列出现有角色及适用部门） |
| `OUT_OF_DATA_SCOPE` | 有角色具备该权限，但适用部门不覆盖目标部门 |
| `TARGET_DEPT_NOT_FOUND` | 目标部门不存在 |
| `ROLE_GRANTED` / `SUPER_ADMIN_BYPASS` | 允许：角色授予 / 超级管理员旁路 |

**设计要点**

- 解释接口与鉴权接口是同一套判定逻辑，结论始终一致（验收用例 T20）。前端不做任何推断，只展示后端的 `trace`。
- 普通用户无法借此接口枚举他人权限：查询他人时，后端先检查调用者的管理范围，不满足就返回 403，界面提示「无权查询该用户」。

## 4. 前端权限控制机制

> 以下机制**全部是体验优化，不是安全机制**。后端对每个接口独立校验，与前端做了什么无关。

### 4.1 三级控制

| 级别 | 机制 | 实现 |
|---|---|---|
| 菜单级 | 无权限的菜单不下发 | `GET /menus/me` 返回已过滤的菜单树 |
| 路由级 | 直接输入 URL 访问无权限页面 → 403 页 | Vue Router 全局前置守卫：路由只从 `/menus/me` 动态注册，未注册的路由落到 403 页 |
| 按钮级 | 无权限的按钮禁用并提示缺少的权限码 | 自定义指令 `v-perm`，数据来自 `GET /auth/me` 的 `permissions` |

```vue
<el-button v-perm="'rbac:user:delete'" @click="remove">删除</el-button>
<el-button v-perm.hide="'rbac:assignment:assign'" @click="assign">分配角色</el-button>
```

**`v-perm` 的行为**

- 默认禁用按钮，悬浮时提示「缺少权限 rbac:user:delete」；`.hide` 修饰符则隐藏按钮。
- 为什么默认禁用而不是隐藏：按钮直接消失时，用户不知道是功能不存在还是自己没权限。
- 前端只判断「是否持有该权限码」。目标对象是否在管理范围内，以后端的 403 / 40302 为准。

### 4.2 权限状态刷新

```typescript
// stores/auth.ts（节选）：登录状态、权限、菜单都在这一个 store 里
const permissions = computed(() => new Set((me.value?.permissions ?? []).map((p) => p.permissionCode)))
function has(code: string): boolean {
  return superAdmin.value || permissions.value.has(code)
}
async function refresh() {
  me.value = await authApi.me()                                        // GET /auth/me
  mustChangePwd.value = me.value.user.mustChangePwd
  menus.value = mustChangePwd.value ? [] : await menuApi.mine()        // GET /menus/me
  loadedAt.value = Date.now()
}
```
**刷新时机**

- 登录后；
- 任何请求返回 403 / 40301 时（说明前端缓存的权限已过期）；
- 路由切换时，距上次刷新超过 1 分钟；
- 撤销自己的指派之后。

后端「权限修改后下一次访问即生效」：每次请求都会重新判定。因此前端缓存只影响按钮状态，不影响能否真正执行。

### 4.3 统一错误处理（axios 响应拦截器）

| 后端返回 | 前端处理 |
|---|---|
| 401（40101 令牌无效 / 已注销 / 口令已改 / 账号已停用） | 清除令牌，跳登录页并带上 `redirect` |
| 403 / 40304 须先改口令 | 跳「修改口令」页 |
| 403 / 40301 无操作权限 | 提示「缺少权限 xxx」，刷新权限状态；整页无权限时显示 403 页 |
| 403 / 40302 超出管理范围、40303 越权授予 | 弹出后端 message（已是中文说明），不跳转 |
| 404 | 提示「目标不存在或已删除」，返回列表 |
| 409 | 提示后端 message（如重复指派、仍被引用、最后一个超级管理员） |
| 400 | 在表单对应字段下方显示 message |
| 鉴权接口 200 且 `allowed = false` | 正常结果，不是错误。权限解释页以红色 DENY 展示 |

## 6. 设计基线、页面状态与交互规则

已经部署、可以运行的控制台就是界面原型的交付物，比静态线框更完整。不过「有界面」不等于「有界面设计文档」。本节写下实现所依据的基线、每类页面的状态，以及全站统一的交互规则。§3 的线框和本节一起构成界面设计，代码是它们的实现。

### 6.1 设计基线

| 项 | 基线 |
|---|---|
| 技术版本 | Vue 3.5.13、Element Plus 2.9.1、Pinia 2.3.1、Vue Router 4.5.0、ECharts 5.6.0、axios 1.7.9；锁定在 `rbac-web/package.json`，不用 `^` 范围 |
| 组件库 | 只用 Element Plus 组件和默认主题，不另写一套样式规范 |
| 主色 | Element Plus 默认蓝 `#409EFF` |
| 语义色 | 允许/成功 `#67C23A`；拒绝/危险 `#F56C6C`；警告 `#E6A23C` |
| 布局 | §2.3：顶栏 + 左侧菜单 + 面包屑 + 主内容区；菜单目录默认展开 |
| 分辨率 | 最小支持 1366×768；移动端不作要求 |
| 文案 | 中文；后端返回的 `message` 已是中文说明，原样展示 |
| 权限码展示 | 等宽字体，四段用不同灰度区分（`PermissionCode` 组件） |
| 作用域展示 | 凡是出现角色的地方都带适用部门，形如「部门经理 @ 道路工程分公司-财务部」 |
| 隐私 | 列表中电话脱敏（138****5678，`maskPhone`），详情页显示完整号码 |
| 页面与菜单 | 页面只通过后端下发菜单的 `componentKey` 注册（`router/routes.ts`），与 `sys_menu.component_key` 一一对应 |

### 6.2 页面状态

每个页面都可能处在下面几种状态，实现方式全站统一：

| 状态 | 触发 | 表现 | 实现 |
|---|---|---|---|
| 加载中 | 请求未返回 | 表格区域显示加载遮罩 | `el-table v-loading` |
| 正常 | 有数据 | §3 的线框 | |
| 空 | 管理范围内没有数据 | 说明为什么为空并给出下一步，例如「管理范围内没有部门，或尚未导入组织数据」 | `el-empty` 带说明文字 |
| 无权限（整页） | 地址栏直接输入没有菜单的路由 | 403 页，说明需要哪项权限 | `ForbiddenView`（`el-result`） |
| 无权限（按钮） | 没有某个权限码 | 按钮禁用，悬浮提示缺少的权限码 | `v-perm`（§4.1） |
| 须先改口令 | 首次登录、口令被重置 | 只能进入「修改口令」，其他路由都被拦下 | 路由守卫 + 40304 处理（§4.3） |
| 未登录或令牌失效 | 401 | 清除令牌，跳登录页并带 `redirect`，登录后回到原页面 | `api/http.ts` 响应拦截器 |
| 操作失败 | 4xx | 顶部提示后端 `message`；表单错误显示在对应字段下 | §4.3 |
| 批量部分成功 | `PARTIAL` 或 `ATOMIC` 未执行 | 显示 `committed`、各项计数和逐人失败清单 | `BatchResultView` |

### 6.3 交互规则

| 规则 | 说明 |
|---|---|
| 危险操作二次确认 | 停用、删除用户，停用、删除角色，回收权限，撤销自己的指派，删除菜单，执行前都要确认。确认框写出影响面，例如「持有该角色的 12 名用户下一次请求即失去该权限」 |
| 撤销自己的指派 | 个人中心和本人的用户详情页都有「回收」按钮。确认框说明恢复只能靠其他管理员重新分配。成功后立即刷新本人的权限和菜单 |
| 结果反馈 | 成功给一句提示；批量操作永远给出完整结果，不只弹一个「操作成功」 |
| 前端不做判断 | 允许与拒绝以后端为准。前端只控制按钮是否可点，范围是否越界以后端返回的 403 / 40302 为准 |
| 判定结果的展示 | 鉴权、解释结果显示实际耗时与是否命中缓存。`allowed = false` 是正常结果，以红色 DENY 展示，不按错误处理 |
| 权限状态刷新 | 登录后、收到 403 / 40301 时、路由切换距上次刷新超过 1 分钟时、撤销自己的指派后（§4.2） |

## 7. 本文档对应的答辩设计点

**DP-5 前端权限控制与动态菜单**

| 项 | 内容 |
|---|---|
| 需求是什么 | 菜单根据用户权限动态生成，没有权限不显示；界面要能说清「权限从哪来、在哪个部门范围内有效」 |
| 存在什么问题 | ① 前端控制常被误当作安全机制；② 菜单若写死在前端，就会与后端权限两处维护、迟早不一致；③ 按钮直接隐藏，用户无法自助申请权限；④ 多部门授权下，同一权限码在不同部门的有效性不同，只列权限码会误导管理员 |
| 采用什么方法与理由 | ① 菜单本身是 MENU 类型资源，`/menus/me` 由后端按「资源:view」过滤后下发，前端不保存菜单配置；② 后端每个接口独立鉴权，演示中主动绕过前端直调接口来证明；③ `v-perm` 默认禁用并提示缺少的权限码；④ 有效权限按「权限码 + 来源角色 + 适用部门」逐行展示，配合权限解释页给出逐步依据 |
| 实现效果 | 后端已实现并测试（T18）：无菜单的用户直接请求接口返回 403；审计员只拿到三个菜单；去掉角色的 `rbac:menu:view` 后，该角色持有者的「菜单管理」随即消失。前端 15 个页面已实现，Playwright 端到端测试在浏览器里验证了普通员工看不到管理菜单、直接访问得到 403 |
