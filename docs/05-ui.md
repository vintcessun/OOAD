# 前端界面设计说明书

**版本 0.1 · 2026 年 9 月 20 日** · 技术栈：Vue 3 + TypeScript + Element Plus + Pinia + ECharts

---

## 1. 设计目标

| # | 目标 | 说明 |
|---|---|---|
| 1 | **让权限可见** | 系统的核心价值是权限关系。界面要回答的不是「有哪些用户」，而是「谁通过什么路径获得了什么权限」 |
| 2 | **让「高并发」可见** | 首页不是「欢迎登录」，而是鉴权吞吐、延迟、缓存命中率的实时面板 |
| 3 | **两种后端共用一套前端** | 通过切换 baseURL 对接结构化/面向对象实现，界面与操作完全一致 |
| 4 | **前端控制仅为体验优化** | 菜单隐藏、按钮禁用不构成安全边界，后端一律独立校验（SRS C-4） |

```
│                             │  子角色：0                      │
│   ── 箭头方向 = 继承方向 ──   │  [解除继承] [查看影响面]        │
└─────────────────────────────┴────────────────────────────────┘
```

**设计要点**

| 项 | 决策与理由 |
|---|---|
| 图形 | 用 **DAG 图**而非树形控件。角色可继承多个角色，树形控件无法表达汇聚节点 |
| 库 | AntV X6 或 Vue Flow（支持 DAG 布局与自定义节点） |
| 箭头方向 | 统一为「子角色 → 父角色」并在图例中标注。父子方向是本功能最易混淆之处，必须在界面上明示 |
| 三段式权限 | 右侧面板固定展示「直接 / 继承 / 最终有效」三段。这是 RBAC1 最需要被理解的概念 |
| 新建继承 | 弹窗选择子/父角色，**提交前先调接口预检**，成环时在图上把环路径高亮为红色 |

> 环检测的错误提示不能只是一句「不能成环」。界面上应当把构成环的那几条边标红，管理员才知道该解除哪一条。这要求后端返回完整环路径（见 `04-api.md` §5.1）——前后端的设计在这里是耦合的，必须一起定。

## 5. 前端权限控制机制

> 再次强调：以下机制**全部是体验优化，不是安全机制**（SRS C-4）。后端对每个接口独立校验，与前端做了什么无关。

### 5.1 三级控制

| 级别 | 机制 | 实现 |
|---|---|---|
| 菜单级 | 无权限的菜单**不下发**（后端过滤） | `GET /menus/mine` 返回已过滤的菜单树 |
| 路由级 | 直接输入 URL 访问无权限页面 → 跳转 403 页 | Vue Router 全局前置守卫校验路由 meta 中声明的权限码 |
| 按钮级 | 无权限的按钮**禁用并提示原因**，而非消失 | 自定义指令 `v-perm` |

### 5.2 `v-perm` 指令

```vue
<el-button v-perm="'system:user:delete'" @click="remove">删除</el-button>
<el-button v-perm.hide="'system:role:assign'" @click="assign">分配角色</el-button>
<el-button v-perm="'oa:doc:draft:approve'" @click="approve">审批</el-button>
```

- 默认行为：**禁用**按钮，并在悬浮时提示「缺少权限 system:user:delete」；
- `.hide` 修饰符：隐藏按钮。

**为什么默认禁用而非隐藏**：按钮直接消失时，用户不知道这个功能是不存在还是自己没权限，只能去问管理员。禁用并说明缺少哪条权限，用户可以直接拿着权限码去申请。仅对涉密功能使用 `.hide`。

### 5.3 权限状态管理

```typescript
// stores/permission.ts
export const usePermissionStore = defineStore('permission', {
  state: () => ({
    permissions: new Set<string>(),   // 有效权限码，登录时从后端获取
    menus: [] as MenuNode[],
  }),
  getters: {
    has: (s) => (code: string) => s.permissions.has(code),
  },
  actions: {
    async refresh() {                  // 权限变更后主动刷新
      const { permissions, menus } = await api.getMe()
      this.permissions = new Set(permissions)
      this.menus = menus
    },
  },
})
```

**刷新时机**（对应 SRS A-12「权限变更立即生效」）：

1. 登录后；
2. 收到后端 `X-Permission-Changed: true` 响应头时（后端在检测到该用户权限已变更时下发）；
3. 路由切换时若距上次刷新超过 5 分钟。

> 演示脚本第 6 步「许禄刷新页面后审批按钮出现」依赖的就是这套机制。若前端把权限缓存到 localStorage 且不主动刷新，就会出现「后端已经放行、前端按钮还是灰的」——演示会当场失败。

## 8. 本文档对应的答辩设计点

**DP-5 前端权限控制与动态菜单**

| 项 | 内容 |
|---|---|
| 需求是什么 | 界面须随用户权限动态变化；权限变更后须立即反映到界面；且要让「权限从哪来」变得可理解 |
| 存在什么问题 | ① 前端控制常被误当作安全机制；② 按钮直接隐藏导致用户无法自助申请权限；③ 权限缓存在前端会导致后端已放行而界面仍禁用；④ 角色继承后，一个用户的 80 条权限的来源无法靠人脑追溯 |
| 采用什么方法与理由 | ① 三级控制（菜单不下发 / 路由守卫 / `v-perm` 指令），同时后端无条件独立校验，并在演示中主动绕过前端来证明；② 默认禁用+提示缺失权限码，仅涉密功能隐藏；③ 三个刷新时机 + 后端 `X-Permission-Changed` 响应头；④ 权限来源溯源表 + DAG 继承图，把推导路径画出来 |
| 实现效果 | 演示脚本第 2 步：绕过前端直调接口仍返回 403；第 5 步：撤销/授予后刷新页面按钮状态立即变化，无需重新登录；用户详情页可逐条指出每条权限的来源路径 |
