## 1. 目标与成功标准

### 1.1 课程目标

在三次检查中取得尽可能靠前的**相对排位**（课程设计为相对给分，70 分对应前 5%）。

### 1.2 与「普通 CRUD 作业」的差异化策略

课程题目原文是「**高负载大并发**的基于 RBAC 模型的权限管理系统」。绝大多数小组会做成「用户 / 角色 / 权限三个 CRUD 页面」。本组的差异化落在七点，每一点都写成可独立陈述的设计点：

| # | 差异点 | 为什么能拿分 |
|---|---|---|
| D-0 | **真实数据全量导入**：111 部门、10000 员工、359 功能点、约 1800 条授予，并产出**数据异常报告** | 多数小组会造三五条假数据。用真实数据跑出来的性能、界面与问题都是真的；异常报告还证明我们逐条校验了老师给的数据 |
| D-1 | **授权内核独立于 CRUD**：`POST /authz/check` 是系统的核心接口，而非 Spring 注解的副产品 | 直接回应「高负载大并发」，且是三种范式对比的共同实验对象 |
| D-2 | **两级缓存 + 事件驱动失效** | 权限变更后的缓存一致性是真实系统的难点，最能体现「设计」而非「实现」 |
| D-3 | **数据范围（数据权限）**：权限清单里的「查看本人」证明功能权限不够用 | 从数据中读出了一条课程框架里没写的需求。字段迭代一就建好、迭代二才启用，展示了「为变化设计」 |
| D-4 | **权限可解释（Explain）**：不仅答 allow/deny，还答「为什么」与推导路径 | 答辩演示效果极强，且完全复用授权内核 |
| D-5 | **约束体系完整**：互斥角色 + **三类**基数约束 + 先决条件角色 | 教师课件明确列出三类基数约束，多数小组只做一类 |
| D-6 | **三范式对比是一次有对照组的实验**：契约测试保证行为等价，8 个维度度量差异 | 课程要求「分别实现」，多数小组交两份代码；我们交两份代码 + 一份实验报告 |

### 1.3 完成定义（Definition of Done）

一个功能算「做完」，必须同时满足：

- [ ] 需求在 `01-srs.md` 中有编号用例，并标注所属迭代
- [ ] 详细设计中有对应设计说明（结构化 / 面向对象至少各一份）
- [ ] 代码在**两种范式模块**中均已实现，且通过同一套契约测试
- [ ] 单元测试已编写，Jacoco 行覆盖率达到 `09-test-plan.md` 规定门槛
- [ ] API 文档 `04-api.md` 已同步
- [ ] 至少一名组员能按「需求→问题→方法与理由→效果」完整陈述该设计

## 2. 工作分解

课程检查为**无领导小组面试**，个人陈述阶段每位同学陈述**文档中的一个设计**。因此工作按**设计点（Design Point）**而非按模块切分——每个设计点是一条从需求到实现的完整纵向切片，可以被独立陈述。

| 设计点 | 职责范围 | 主文档 |
|---|---|---|
| **DP-1 三范式并行架构** | 多模块划分、契约设计、CI、范式准入标准与对比实验 | `02-architecture.md` §3 §5<br/>`10-paradigm-comparison.md` |
| **DP-2 授权判定内核与两级缓存失效** | 判定管道、有效权限计算、两级缓存、事件驱动失效、权限解释 | `02-architecture.md` §4.1 §4.2<br/>`04-api.md` §2 |
| **DP-3 角色继承的图模型与环检测** | 继承 DAG、传递闭包、环检测、权限来源溯源 | `02-architecture.md` §4.3<br/>`07-detail-oo.md` |
| **DP-4 约束规则的可扩展设计** | 互斥角色、三类基数约束、先决条件角色、可扩展性验收实验 | `02-architecture.md` §4.4<br/>`08-detail-functional.md` |
| **DP-5 前端权限控制与动态菜单** | 界面设计、三级权限控制、继承图可视化、约束配置向导 | `05-ui.md` |
| **DP-6 组织架构、数据范围与数据模型** | 数据模型、三份 xlsx 导入（层级校验、同名消歧、单元格归一化、岗位→角色派生、异常报告）、数据范围、测试与 Jacoco | `03-database.md`<br/>`09-test-plan.md` |

**为什么按纵向切片而非横向分层**：个人陈述要求讲清「需求是什么、为什么这么设计、效果如何」。若按「有人写前端、有人写后端」横向切分，没有人能讲出一条完整链路。

每个设计点在其主文档的**末节**都有固定的四段式说明（需求 / 问题 / 方法与理由 / 效果），讲稿模板见 [`11-defense.md`](11-defense.md)。

## 4. 协作规范

### 4.1 分支策略

```
main            受保护，只接受 PR 合入，任何时刻可运行
├── feat/xxx    功能分支，命名 feat/<模块>-<简述>，如 feat/authz-cache
├── docs/xxx    文档分支
└── fix/xxx     缺陷修复
```

### 4.2 提交信息

```
<type>(<scope>): <简述>

type:  feat | fix | docs | test | refactor | perf | chore
scope: srs | db | api | ui | structured | oo | functional | authz | test
```

示例：`feat(structured): 实现 RBAC0 用户角色分配用例 IDM-003`

### 4.3 文档约定

- 所有文档为 **Markdown**，正文中文，文件名用 ASCII slug（避免 Windows / Git 中文路径问题）。
- 图表优先用 **Mermaid**（GitHub 原生渲染），用例图用 PlantUML。
- **最终提交给老师的版本，图需在 StarUML 中重绘**并导出，`.mdj` 源文件存 `diagrams/`。课程明确建议采用 StarUML。
- 需求一旦有编号（如 `RBAC-REQ-AUTHZ-001`），**不得改编号**，废弃则标注「已废弃」保留占位。

### 4.4 代码约定

- 两个范式模块**必须实现同一份 `rbac-contract` 接口**，否则无法横向对比。
- 结构化模块**禁止**使用继承与多态，数据用贫血的 record / POJO，逻辑全在无状态的 `XxxFunctions` 静态方法中——这是「面向功能」的定义，不能写成「披着过程外衣的 OO」。完整准入标准见 `06-detail-structured.md` §1.2。
- **原始 xlsx 不入库**：员工信息表含一万条真实姓名与手机号，`.gitignore` 已排除 `data/raw/*.xlsx`，组员自行从课程网站下载。
- 每个 PR 必须附带 Jacoco 覆盖率变化，覆盖率下降的 PR 不合入。
