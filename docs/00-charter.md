## 1. 目标与成功标准

### 1.1 课程目标

在三次检查中取得尽可能靠前的**相对排位**（课程设计为相对给分，70 分对应前 5%）。

### 1.2 与「普通 CRUD 作业」的差异化策略

需求清单明确不要求高并发专项设计，差异化落在**设计的正确性与可验证性**上，每一点都能用测试或真实数据演示：

| # | 差异点 | 证据 |
|---|---|---|
| D-0 | **真实数据全量导入**，并产出异常清单 | 111 部门、10,000 人全部定位；18 / 115 / 359 / 1,795 / 3,190；2 个重名负责人进异常清单（`03-database.md` §5.4） |
| D-1 | **作用域跟着指派走**：多部门权限不会拼出不存在的授权 | T07、T07b |
| D-2 | **带版本号的授权缓存**：下一次访问即生效，多副本也成立 | T12、T13、T22 |
| D-3 | **管理范围 + 授权上界**：管理员只能管以下层级，不能授出自己没有的权限，回收不级联 | T08–T10、T14 |
| D-4 | **契约驱动的统一鉴权**，启动时双向核对契约与实现 | 45 个接口；契约外路由 403 |
| D-5 | **权限可解释**：与鉴权共用同一个判定过程 | T20：七组输入结论全同 |
| D-6 | **验收测试连真实数据库**：T01–T22 经 HTTP 调用；前端端到端测试连真实后端 | 后端 69 个测试，行覆盖率 97%；前端 42 + 9 个测试 |

### 1.3 完成定义（Definition of Done）

一个功能算「做完」，必须同时满足：

- [ ] 需求在 `01-srs.md` 中有编号用例，并标注所属迭代
- [ ] 详细设计（`06-detail-structured.md`）中有对应的处理规约
- [ ] 接口在契约中声明了所需权限，且有经 HTTP 调用的集成测试
- [ ] 单元测试已编写，Jacoco 行覆盖率达到 `09-test-plan.md` 规定门槛
- [ ] API 文档 `04-api.md` 已同步
- [ ] 至少一名组员能按「需求→问题→方法与理由→效果」完整陈述该设计
- [ ] **可自动测试**：`mvn verify` 一条命令跑完全部测试，CI 全绿，无任何手工步骤
- [ ] **可部署**：`docker compose up` 一条命令拉起完整环境，`/actuator/health` 返回 UP

## 2. 工作分解

课程检查为**无领导小组面试**，个人陈述阶段每位同学陈述**文档中的一个设计**。因此工作按**设计点（Design Point）**而非按模块切分——每个设计点是一条从需求到实现的完整纵向切片，可以被独立陈述。

| 设计点 | 职责范围 | 主文档 |
|---|---|---|
| **DP-1 权限判定的功能分解与作用域** | 功能分解、DFD、判定过程、权限解释 | `06-detail-structured.md` §2、§5.2<br/>`02-architecture.md` §4.1 |
| **DP-2 带版本号的授权缓存** | Redis 授权缓存、失效时机、令牌注销 | `02-architecture.md` §4.2、§4.3 |
| **DP-3 管理范围与授权上界** | 分级管理、分配与回收、角色管理 | `06-detail-structured.md` §5.3–§5.6 |
| **DP-4 批量授权与数据导入** | 三份 xlsx 导入、异常清单、按分公司 / 部门 / 员工批量授权 | `03-database.md` §5<br/>`06-detail-structured.md` §5.5 |
| **DP-5 契约驱动的统一鉴权与动态菜单** | OpenAPI 契约、拦截器、前端界面设计 | `04-api.md`、`05-ui.md` |
| **DP-6 数据模型** | 多公司、部门树、指派作用域、外键、审计表 | `03-database.md` |

**为什么按纵向切片而非横向分层**：个人陈述要求讲清「需求是什么、为什么这么设计、效果如何」。若按「有人写前端、有人写后端」横向切分，没有人能讲出一条完整链路。

组内提过按「数据库与缓存、前端、后端、API」四个方面分工。这四个方面仍然存在，只是作为**每个设计点内部**的切面，而不是分工单位：

| 方面 | 主要落在 |
|---|---|
| 数据库与缓存 | DP-6（数据模型）、DP-2（缓存） |
| 前端 | DP-5 |
| 后端 | DP-1（判定）、DP-3（管理）、DP-4（批量与导入） |
| API | 各设计点对应的接口；「所有接口受权限控制」归 DP-5（`04-api.md` §1.4） |

每个设计点在其主文档的**末节**都有固定的四段式说明（需求 / 问题 / 方法与理由 / 效果），讲稿模板见 [`11-defense.md`](11-defense.md)。

## 4. 协作规范

### 4.1 分支策略

```
main            受保护，只接受 PR 合入，任何时刻可运行
├── feat/xxx    功能分支，命名 feat/<模块>-<简述>，如 feat/authz-cache
├── docs/xxx    文档分支
└── fix/xxx     缺陷修复
```

### 4.2 提交信息

```
<type>(<scope>): <简述>

type:  feat | fix | docs | test | refactor | perf | chore
scope: srs | db | api | ui | structured | oo | functional | authz | test
```

示例：`feat(structured): 实现 RBAC0 用户角色分配用例 IDM-003`

### 4.3 文档约定

- 所有文档为 **Markdown**，正文中文，文件名用 ASCII slug（避免 Windows / Git 中文路径问题）。
- 图表优先用 **Mermaid**（GitHub 原生渲染），用例图用 PlantUML。
- **最终提交给老师的版本，图需在 StarUML 中重绘**并导出，`.mdj` 源文件存 `diagrams/`。课程明确建议采用 StarUML。
- 需求一旦有编号（如 `RBAC-REQ-AUTHZ-001`），**不得改编号**，废弃则标注「已废弃」保留占位。

### 4.4 代码约定

- 两个范式模块**必须实现同一份 `rbac-contract` 接口**，否则无法横向对比。
- 结构化模块**禁止**使用继承与多态，数据用贫血的 record / POJO，逻辑全在无状态的 `XxxFunctions` 静态方法中——这是「面向功能」的定义，不能写成「披着过程外衣的 OO」。完整准入标准见 `06-detail-structured.md` §1.2。
- **工具版本统一**：JDK 21（服务器 21.0.2）、Maven 3.9.9。仓库自带 `./mvnw`，本机没装 Maven 也能构建；依赖一律走华为云镜像（`-s deploy/maven-settings-huawei.xml`）。
- **原始 xlsx 不入库**：员工信息表含一万条真实姓名与手机号，`.gitignore` 已排除 `data/raw/*.xlsx`，组员自行从课程网站下载。
- 每个 PR 必须附带 Jacoco 覆盖率变化，覆盖率下降的 PR 不合入。
